# orchestra-dsh 深度对齐共识备忘录（2026-09-16）

> 本文档由人类用户与顾问 Agent 在深度探讨对齐过程中逐项梳理并持续追加。
> 它代表人类用户对本插件最真实的生产期望，作为后续所有代码重构、瘦身与开发的最高权威依据。

---

## 模块 1：产品定位与业务边界

### 1. 两半结构定位
* **A2A（跨进程沟通管理）**：
  * 是整套插件的底层通信底座，也是一个独立完备的轻量协作工作台。
  * 专为轻量级、短平快的多会话协作设计（如两三个 Session 临时碰头、交接上下文、一个调研一个编写）。
  * 占日常使用场景的约 50%。
* **Orchestra（多线任务编排）**：
  * 长在 A2A 底座之上，服务于中大型项目的复杂研发推进。
  * 当任务体量大、需要严格的角色分工与多阶段协作时启用。
* **业务执行流范式**：
  * 典型推进链路：`A (调研) → [B (开发) ⇄ C (验证/审查)] → 汇报 Driver → (合并/推送)`。
  * **前线自治原则**：节点间直接交接硬事实，B 与 C 在前线形成上限为 2 轮的自洽小闭环，**坚决不让 Driver 当传话筒**。
  * **Driver 纯粹静默与事件唤醒**：Driver 在 Worker 干活时保持静默（不搞阻塞轮询，也不插手实现与 Review），多线并发时被动等待前线完成消息唤醒。
  * **必须拆分独立 Session**：坚决反对一个 Session 一锅端（上下文超过 50% 必出现注意力稀释与偏见遗漏）；独立 Session 能形成客观公正的“对抗审视”。
  * **交接铁律**：A 给 B 交接任务时，**只带 Hard Fact（硬事实/重现步骤/改动位置），不带主观假设和推测**，不污染下一个 Session 的独立判断。

### 2. 异质性与环境边界
* **完全聚焦 DSH 内部**：坚决不管外部 CLI 工具（不驱动外部 Claude Code / Pi / Codex），角色异质性完全由 DSH 内部不同的 Preset、模型和思考强度决定。
* **验证环境纪律**：用户日常使用的 Web Profile（端口 4599）绝对不装未确认版本；所有改动与验证必须在专用靶场（端口 4600 的 dev profile）用真实浏览器（ego-browser / ego-lite）实测通过。

## 模块 2：底座通信与会话管理面

### 1. 动作面全家桶
* **插话（`steer`）**：在目标当前思考间隙插入指示，中途纠偏。
* **停止（`cancel` / `stop` / `abort`）**：
  * **[重大对齐新增]**：底座必须提供显式的停止能力（对应 Composer 的 Stop 按钮，底层调用 `agent.cancel()`），能够瞬间掐断目标会话正在跑的推理和工具，清空队列，防止跑疯。
* **改名（`rename`）**：随时调整会话标题标签。
* **归档（`archive`）**：任务结束时折叠冷藏，保持侧边栏清爽。

### 2. 会话发现性（`a2a_list`）优化
* 必须支持按当前项目（CWD）最近活跃度降序排列。
* 明确暴露硬事实字段：CWD、相对活跃时间（如 5m ago）、角色标签。
* 支持按会话名称关键词精准/模糊快速搜索，使 Driver 能在秒级定位到数十小时前的特定历史会话。

### 3. 会话阅读边界（`a2a_read`）
* **倒序渐进披露（Progressive Disclosure）**：
  * 默认仅倒着阅读目标会话最近的 1~2 轮交互，杜绝一次性拉取全文撑爆自身上下文。
  * 支持传参按需向前翻阅更多轮次。
  * 深度历史分析交由专业外置工具（如 OBELISK 插件/skill）。

## 模块 3：记录载体与权威模型

### 1. 资产落盘内外双轨制
* **内部账本（插件底座现场）**：
  * 统一定位在项目工作区根目录的 **`.orchestra/`**（加点隐藏，保持整洁）。
  * 仅存放支撑插件底座运行的元数据：会话映射表、投递回执、守护定时器、运行日志。
* **外部资产（项目自身的业务治理文档）**：
  * **坚决尊重并服从当前项目自有的治理规则（Governance）**。
  * 如果项目规范要求在根目录维护 `PROGRESS.md`，或在 `docs/tasks/` 放任务单、在 `docs/receipts/` 放验收证明，Driver 必须如实产出并提交到 Git 仓库规定位置。
  * 杜绝“用了编排插件却导致项目仓库里过程文档一片空白”的自嗨行为。

### 2. Driver 换代交接规则
* **项目文书交接**：上一代 Driver 在上下文快满前，在项目规定的看板中留下清晰的状态指针（已完成批次、当前阻塞点、下一个目标）。
* **底座现场快照**：新一代 Driver 开局读完项目看板后，通过底座工具一次性获取当前依然存活的 Worker 清单及其最新状态，1 回合完成无缝接管，杜绝盲目重复拉人。

## 模块 4：节点模型与图结构

### 1. 节点形态与 ADR-0010 决断
* **默认开启独立 Session**：确认 ADR-0010 维持现状，默认全部为独立会话，以保证完整的工具面、独立的预设定制与干净的上下文。
* **常驻杂活会话优于泛滥的 Subagent**：对于频繁出现的通用打杂任务（如 `code-scout` 搜寻代码），由 Driver 维持一个常驻独立 Session 专门做，比每个节点到处临时乱开 Subagent 更加节省 Token 且行为可控。
* **工作流拓扑结构**：确认以带有局部 Loop（上限通常为 2 轮）的有向无环图（DAG）为主干形态。

### 2. DSH 原生机制深入查证结论
* **Preset 的定制深度**：
  * Preset 是基于 Cordis 的 **Agent-Plane 完整组合**（`agent.cordis.yml`）。
  * 除了系统自带的 4 个默认 preset，用户在 `~/.dsh/.agent-presets/` 或项目内自定义的 preset 可以深度定制：Persona、Agent-Instructions、Tools（自由配置或屏蔽任意工具）、Skills 挂载与专属隔离域。
* **原生 Subagent 的底层事实**：
  * **开启形式**：必须使用 `spawn`（纯净无父历史，仅带当前提示词），绝不能用 `fork`（会完整克隆父历史，极耗上下文）。
  * **层级深度**：原生支持递归嵌套（`delegationDepth`，从父到子、孙）。
  * **通信与通信边界**：基础 `dsh-subagent` 严格限定于相邻父子边通信；官方实验性 `agent-team` 引入了 Peer Mailbox 机制实现同级通信。
* **并行与串行的工程取舍（关键认知）**：
  * 盲目拆分并行是软件工程的大忌！即便多个文件没有物理写冲突，也往往存在接口与管线的隐性耦合。
  * 只有完全正交且无逻辑依赖的任务才适合并行分发；有耦合的代码修改，由同一个 Session 顺次串行修改效果显著更优（避免接口断层与跨会话通信成本）。

## 模块 5：编排运行时与脚手架瘦身

### 1. 审批与启动极简化
* **推翻死板的 Slash 命令**：废除 `/team approve <draftId>@<revision>` 强行要求。
* **白话自然语言批准**：用户在对话中自然回复“启动”、“可以”、“ok”，底座监听真实用户消息回合，自动绑定最后展示的计划并解冻执行。

### 2. 拔除 17 类微观状态机工具（彻底瘦身）
* **大刀阔斧删除**：彻底拔除 `orchestra_loop_start`、`orchestra_attempt_start`、`orchestra_verdict`、`orchestra_handoff`、`orchestra_gate_open`、`orchestra_gate_fallback`、`orchestra_reconcile` 等繁文缛节工具。
* **解放 Driver**：Driver 不再充当底层状态机的“打卡员”，杜绝无意义的 RPC 调用淹没上下文。
* **收敛为 5 大核心工具**：
  1. `orchestra_draft`：起草车道规划与阶段概览；
  2. `orchestra_dispatch`：按需派活单（如果对应角色会话不存在则顺手创建，无需繁复的独立 spawn）；
  3. `orchestra_wait`：静默挂起等待前线事件唤醒（杜绝轮询消耗）；
  4. `orchestra_team`：提供客观事实比对看板（真实存活态、Git 提交存在性、收据文件存在性）；
  5. `orchestra_dismiss` / `orchestra_activate`：结案归档与换代复苏。

### 3. 车道模型（Lane-based Routing）
* 编排无需一开始画出几十行参数的庞然大物。
* 拆分为具体的**车道（Lane）**：如车道 A 对应一条具体的任务线（含 2~3 个节点和一个小闭环）。
* 车道文件（如任务单或轻量 DAG 说明）由该车道上的所有参与会话共享查阅，节点启动时即明确：“我在哪条道、我的职责是什么、做完把硬事实交接给谁”。

### 4. 聪明防失控护栏（Smart Safeguards 代替死板 Budget）
* **死板 Budget 的弊端**：生硬限制 30 分钟、固定 1 亿 Token 或硬卡并发数，极易误杀正在正常收尾的合法长任务。
* **聪明的实际防失控护栏**：
  1. **尝试上限（Attempt Cap = 2 轮）**：同一任务修改或复核超过 2 轮直接中断，判定角色能力触顶，强制弹回 Driver 裁决，防止二人转死循环；
  2. **僵死检测（Stall / Inactivity Timeout）**：Worker 超过合理阈值（如 10 分钟）没有任何输出、工具调用或进度更新，底座标记为失联并唤醒 Driver 介入；
  3. **防无限繁殖（Anti-Runaway Spawn）**：限制单条车道内的最大未结案会话数，防止逻辑跑飞时一轮新建几十个幽灵会话。
