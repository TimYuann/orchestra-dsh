## 2. 执行计划必须包含的内容（缺一项即被退回）

1. **任务分解**：把 P0–P4 拆成可独立验收的工作项；每项写**负责面**（哪个文件/模块）、**输入**、**产出**、**退出判据**。
2. **文件级改动清单**：新增/修改/删除的文件，逐个写"改什么、为什么、属于哪条需求（A1…F1′）"。
3. **实现顺序**：先减法（S1–S6）→ 再 P0 …；标明**每一步的前置依赖**（例如"预设进名册"依赖 B 决策的部署步骤）。
4. **每条验收的可执行验证方式**：N1–N7 逐条给出"怎么造这个负例、期望看到什么拒绝、拒绝时留下的记录是什么"。**不接受"应当会拒绝"这种写法**——要给出可执行的注入方式。
5. **验收脚本**：宿主执行层要跑的脚本，逐条写"命令、cwd、环境、期望退出码、期望摘要、输出如何判定"；并说明**运行前提声明**怎么记录（树/环境/模式/外呼）。
6. **记录与字段**：节点记录、候选身份、胶囊、决策队列、豁免集、四节体检报告的**字段表与 schema 版本**。
7. **部署步骤**：profile 的 `agent-presets` 行加 `roots`（**直接改已有行**，不要用插件补丁文件）、重启时机、验证方式（从外部核实际挂载的组合）。
8. **风险与回退**：每一步"如果失败会怎样、怎么退"，以及**哪些步骤不可回退**。
9. **agent 侧预算**：每个节点**新增的工具调用/轮次预算**（目标：2–3 次），以及 `ratio{plan, implement, verify}` 的记录方式。

## 3. 计划门审核标准（Session 1 按这**十二**条判：**先判 0.1–0.3 三条硬检查**，再逐条判 1–9；通过与退回都要逐条给结论）

**0.1–0.3 硬检查项（一等条目，来自 Pro 审核的"三个最先坏的点"；缺任一 ⇒ 直接退回）**

- **0.1 冻结快照执行**：计划是否明确"验收**从冻结快照执行**"（`git worktree add --detach <tree>` 或等价），**额外输入（夹具 / env 文件）按哈希显式绑定**；外呼观测不完整是否正确记 `unknown`（**关键前提未知不得判合格**）。
- **0.2 活跃租约冲突必须阻断**：是否明确"**越界触及他人活跃租约 ⇒ 阻断冻结/合并**"，且**豁免不得取消该冲突**；对账报告是否打印**当次全量豁免集**（每条带理由/加入人/时间）。
- **0.3 ref 更新必须带预期旧值**：是否给出 `git update-ref <ref> <new> <expected-old>` 形式的**原子更新**，以及"**ref 已推进、记账前崩溃**"的**幂等恢复**方案。缺此视为未通过（树比对不是 CAS）。

1. **需求可追溯**：每条要求（A–F 各组 + 元规则）都能指到具体落地动作；指不到的必须显式标注"延后/不做 + 理由"。
2. **验收可执行**：N1–N7 每条都有可执行的注入方式与判定条件；**没有"应当""理论上"这类词**。
3. **阶段有闸**：每个阶段有明确退出判据，且判据是**可机器判定**的。
4. **拒绝点明确**：凡声称"会被拒绝/会被拦"的地方，必须写出**在哪一点拒绝、拒绝时返回什么类型化原因**；做不到的改写成"事后点名"。
5. **不越界**：严格守住契约 §0 三条约束（门只在插件拥有的动作上 / 事实只由插件写 / 严格压在宿主能重算处）。
6. **不新增机制**：任何契约之外的新机制必须带 `fault_ref`（指向一次已付过成本的实例），否则退回。
7. **不做清单被遵守**：开工前完备度闸、词汇闸、整批拒的原子收工、自己遍历文件算树、用 `index.lock` 判写者——一条都不许出现。
8. **不把未验证写成现状**：凡尚未实现的，措辞必须是"将/计划"，不得写成"已"。
9. **agent 侧不增厚**：新增的 agent 侧动作合计不超过每节点 2–3 次工具调用；超出必须说明为什么不能由宿主承担。
