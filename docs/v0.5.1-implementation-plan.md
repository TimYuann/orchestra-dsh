# Implementation Plan: orchestra-dsh v0.5.1 Multi-Lane Concurrency, Lazy Fleet, Re-entry Arbitration & Model Preferences

v0.5.1 旨在彻底解决多车道协作下的并发竞争、同 CWD 重入死锁、舰队过早拉起（Ghost Sessions / Token 浪费）、任务拆解中的智力与心智负荷分配，以及多模型异构偏好持久化。

---

## 核心设计与决策对齐

### 1. 状态并发安全 (`ActiveTeamStateStore.mutate`)
- **问题根因**：多车道并发运行时，多个 Worker 几乎同时调用 `orchestra_report`。由于 `ActiveTeamStateStore.replace` 依赖版本 CAS 检查，无重试机制导致 4 车道并发测试中有 75% 的报送遭遇 `stale_write` 被直接丢弃。
- **CAS 重试引擎**：
  - 在 `src/orchestra-state.ts` 中实现 `activeTeamState.mutate(cwd, updater, { maxRetries: 5, baseBackoffMs: 8, maxBackoffMs: 128 })`。
  - 带 Full-jitter 的指数退避，遇到 `FS_STALE_VERSION` 自动重新读取最新 snapshot 并重新计算。
  - **纯函数契约断言**：`updater(team)` 必须是纯函数（禁止包含 I/O、Session 创建或网络消息），在重试前比对输入快照指纹，防止副作用污染。
- **总线去抖（Commit-only Signal）**：
  - 更新 `src/team-change-bus.ts` 中的 `withChangeSignal`，代理拦截 `mutate`。
  - 确保无论经历多少次重试，**仅在底层 CAS 最终成功写入磁盘后触发一次 `teamChange` 广播**，杜绝重试期间产生幽灵事件。
- **幂等 `orchestra_report`**：
  - 先将报告 Markdown 幂等写入磁盘落盘文件（`orchestra/reports/<path>`）。
  - 计算确定性 `reportId = sha256(teamId + roleId + canonicalPath + contentHash)`。
  - 通过 `activeTeamState.mutate` 原子更新账本：若 `reportId` 已存在则跳过，否则追加至 `reports[]` 并递增 `role.reportCount` 与更新 `role.lastReport`。

---

### 2. 编队生命周期、懒加载与后门修补

- **彻底封死 `dispatchRoleTask` 中的 `isNewTeam` 后门**：
  - 删除 `src/orchestra.ts` 中 `if (isNewTeam) await activeTeamState.create(...)` 逻辑。
  - 若调用 `orchestra_dispatch` 时当前 CWD 没有经审批并创建的活跃 Team，直接抛出致命错误，坚决捍卫宪章治理底线。
- **`orchestra_create` 仅预约（Reserve-only）**：
  - 创建 Team 时只在 `roles` 中预分配 Session ID 与 Child ID，并将状态标记为 `phase: "reserved"`。
  - **零创建 Session、零拉起 Subagent、零发送迎新词**，避免给系统和 A2A list 造成负担，消除 Ghost Sessions。
- **`orchestra_dispatch` 按需懒加载物化**：
  - 首次 dispatch 某个角色时，检测到 `phase === "reserved"`，执行两阶段 CAS：`reserved -> provisioning -> active`。
  - 在此时才调用 `createSession` 或 `subagents.create`。
  - **合并首回合**：将角色的 System Prompt / 欢迎协议词与本次派发的具体 Task 合并为单次回合，节省一轮空的握手 Token。

### 3. 同 CWD 重入仲裁 (Re-entry Arbitration)

- **放弃第二套锁**：不搞租约服务（Lease）或 `team.lock`，继续由 `orchestra/state/team.json` 唯一 CAS 记录判定。
- **`/team` 重入预检逻辑**：
  1. **`terminal` 状态**（`completed` / `failed` / `abandoned`）：无缝自动归档历史团队，直接进入新团队创建，零打扰。
  2. **`orphaned_idle` 状态**（Controller 已离线，且所有 Worker 无 running / pending 任务）：给出极短二选一提示——「接管旧团队继续工作」还是「归档旧团队并开始新任务」？
     - 若接管：调用领域函数 `transferOrchestrationControl` 原子交接 `team.controllerSessionId` 与 `document.semanticWriterSessionId`；针对 Subagent 角色，重置为 `reserved` 并绑定新 Controller。
     - 若新建：归档旧队后进入新任务 onboarding。
  3. **`foreign_busy` 状态**（仍有 Worker 正在运行）：展示正在运行的角色，拒绝自动抢夺。若要放弃旧团队，必须由真实人类用户（`source.kind === "user"`）确认后才允许 force-archive。

### 4. 任务拆解与智力分配 (Macro Charter vs Micro Task Card)

- **核心模型**：$\text{Worker 成本} \approx \text{任务剩余熵} \times \text{模型单价}$。
- **宏观与微观分层**：
  - **Macro Charter**：Driver 与用户通过自然语言对齐，定义目标、阶段划分、车道、角色与验收准则。人类一次审批。
  - **Micro Task Card（JIT 即时生成）**：在每条 Lane 执行前落盘到 `orchestra/tasks/<phase>-<lane>.md`。只要没有改变 Charter 设定的边界，不需要反复打扰人类。
- **适度规模原则（RIGHT-SIZE / 非必要不扩大原则）**：
  - 低熵任务（文件与方案已知）：Driver 自己写 3~5 句话的 Task Card，不拉起 Planner。
  - 高熵任务（落点未知、架构推演）：Driver 派发给预置的 `planner / architect`。
- **按需懒加载的 Planner 角色**：
  - 在 Synthetic Topology 中预声明 `planner / architect`，初始标记为 `reserved`。
  - 若本次任务简单，Planner 永远不被物化，成本为 0。
  - 若为高熵任务，Driver 派发给 Planner，Planner 调研后输出 Task Card 文件，并**仅向 Driver 返回硬事实与文件路径**。Driver 将路径下发给 Worker（Luna / Flash）。Driver 上下文开销保持在 $O(\text{lanes})$。

### 5. Archive 完整性、断点续做与安全注销 (`orchestra_dismiss`)

- **归档完整性**：
  - `orchestra_archive` 快照完整保存 `mission`、`document`（活体修订、决策记录）、`graphRuntime`（DAG 进度）、`roles` 与 `reports`。
  - 增强 `orchestra_dismiss`：支持参数 `reason?: string` 与 `summary?: string`，自动捕获退出瞬间的未尽任务快照并写入 `handoffSummary`，确保后续 Agent 读取归档即知“完成了什么、遗留了什么”。
  - `orchestra_activate` 原生支持通过 `archiveId` 重建或激活团队，并向角色派发 Recovery Packet 恢复断点。
- **安全注销生命周期**：
  - 严格校验 Controller 权限（`caller === controllerSessionId`）。
  - 先生成不可变归档，CAS 状态为 `dismissed`。
  - 分叉式清理：存活 Session 发送 `wake: false` 退休通知并 cancel；休眠 Session 跳过（绝不反向唤醒）；子 Agent 调用 `drainContinuableChildren` 回收。

---

### 6. 模型偏好记忆与全景蓝图展示

- **偏好持久化**：
  - 项目根目录下维护 `orchestra/preferences.json`（支持全局 fallback `~/.dsh/orchestra-preferences.json`）。
  - 分级维护模型阶梯：
    - `high_intelligence`（Planner / Architect / Oracle / Driver）：例如 `chatgpt-4o` 或 `deepseek-v4.1-pro`，`reasoningEffort: "high"`
    - `standard_work`（Implementer / Reviewer）：例如 `deepseek-v4.1`，`reasoningEffort: "medium"`
    - `fast_verification`（Verifier / 测试）：例如 `deepseek-v4.1-flash`，`reasoningEffort: "low"`
- **首次问询与继承**：
  - 项目首次使用 `/team` 或 `orchestra_draft` 时，若未发现偏好，Driver 主动向用户确认偏好，并持久化到文件。
- **全景蓝图呈现**：
  - 在 `orchestra_draft` 呈现的任务蓝图大表中，完整展现 `角色 | 阶段/车道 | backend | model | reasoningEffort | 职责`，让用户在批准 Charter 时对整支舰队的算力阶梯一清二楚。
