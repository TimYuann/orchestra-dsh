## 1. Q1 裁定：日常体量判断 = scout 方案（含最小规范）

### 1.1 为什么不是"取一方"

三方的表述其实不在同一个层面上，所以"二选一"是个假选择：

- **GPT Pro 主张**的是**门槛原则**："判断权放 driver，插件提供事实并守住不可降低的门槛"。这条**成立**，且是本裁定的地基。
- **Owner 主张**的是**执行手段**：driver 在勾勒队伍前需要足够判断，且需要保护上下文健康度 ⇒ 用 scout sub-agent。这条**成立**，且不与前者冲突。
- **Session 1 主张**（此前附议 Pro 版、未提 scout）**不构成对立方案**，它只是没有给手段。

**裁定**：门槛原则按 Pro；手段按 Owner；两者用一条**权限隔离线**缝起来（§1.3）。**不加第二个分类器**（采 Pro："不值得让每次'两人聊一下'先多付一次分类成本"）。

### 1.2 scout 最小规范（可直接落进计划 §0.5）

| 项 | 规范 |
|---|---|
| **调用时机** | 每 mission **一次**侦察（recon），在 driver 勾勒队伍**之前**；如需按车道细分，**每车道至多一次**。**不是每回合调用**，不在回合循环里 |
| **输入** | driver 的固定 prompt（一次写定、可复用）+ **只读**的 mission 事实：需求/计划文件路径、仓库 commit、现有工具与角色名册 |
| **输出**（结构化，落盘复用） | ① **`normalizable` 判定** + 依据（是否要读函数、是否要看代码、是否需要真实执行）② **车道粗拆**（lane → 一句话职责）③ **每车道难度与规模估计**（S/M/L + 依据）④ **未决项与未知**（显式列出，不许留空壳） |
| **判据** | scout **只写事实与估计**；每条估计必须带依据指针（文件/路径/命令）。**禁止**输出"这个任务不需要交付层"这类**授权性结论**——那是 §1.3 的禁区 |
| **成本上限** | 1 次 recon + 每车道 1 次 = **≤ 5 个 scout**（按当前车道规模）；每 scout **1–2 轮**；**不递归**（scout 不得再派 scout）；工具面 = 只读（无交付动作、无写面） |
| **与 driver 的关系** | scout **并行存在、不互斥**（Owner 原话）；scout **不阻塞** driver 开工，driver 可先动手再吸收其结论 |
| **产出归属** | 侦察结论是**任务记录的一部分**，不是用过即弃的草稿（Owner 原话）——它是后续车道派活的输入 |
| **实现落点** | scout = DSH **原生 subagent**（`a2a_create(execution:"subagent")`；活体证据见 `STATE.md` §M1：子节点落盘 `origin:"subagent"`、`approval/policy:{policy:"never"}`、子节点真实执行并回报）⇒ **零新增插件机制**，正好承接 Pro"不值得再加一个便宜分类器"；**不进 P0 代码范围**（P0 = D1/D2/D3 + 其真正依赖的 S 项），作为 driver 侧口径随 `orchestration-principles` skill / 角色 persona 的后续版本落地 |

### 1.3 它与"分档只看插件可见的交付事实"如何衔接（本裁定的关键一条）

**唯一分界线**：

> **scout 的难度估计 = 建议性元数据，永远不能把交付型节点降成档 0，也不能免除任何门槛。**

理由：`plan-0.8.0-execution.md:105` 已把准入写成只认三样——**插件可见的交付动作 / 产物引用 / 依赖**——并明文 **"不采信 driver 的『不交付』标签"**（证据：`plan-0.8.0-execution.md:105` ⑤；`:110` 用例 4）。如果 scout 的"这任务很轻"能改档位，那等于**绕过同一份文档已经写死的"不采信标签"原则**，只是把标签从 driver 换成了 scout。

因此衔接形态是：

1. **插件侧（权威）**：档位只由机械谓词算出（`plan-0.8.0-execution.md:106–112` 五条 + 五个用例）。
2. **scout 侧（建议）**：难度估计用于**选预设、定车道、估预算**，不进入档位判定函数。
3. **方向不对称**：scout 说"轻"**不放松**任何门槛；scout 说"重"**可以**让 driver 主动加严（多派审查、提前开决策记录）——加严不需要授权。
4. **规模估计允许出错**：承接 Pro 原话——"规模估计可以错，错误估计不得让交付越过底线"。因为档位不是 scout 给的，估错不产生越权。

## 2. Q2 裁定：关键事实的出处要求（措辞定稿）

### 2.1 采纳文本

**采 GPT Pro 收窄版**（与 `p0-scope-ruling.md:16` 记录的 H3 收窄一致），定稿措辞：

> **出处要求只作用于「将被升级为执行依据的关键事实」**，不作用于全部陈述。
> 关键事实在**三个入口**（报告提交 / 任务派发 / 方案采纳）绑定三元组：**陈述 — 固定版本来源或实测记录 — 适用范围**。
> **宿主只做机械核验**：引用能否解析、版本是否匹配、实测记录是否确实存在。
> **实质判断「材料是否支持结论」由独立审查者作出**——宿主不得代替。
> **无证据不得升级为"已验证前提"**；但**允许**明确标成**假设**并授权**一次有界探针**。
> **被拒绝的是"无证据地授予资格"，不是"说出一个不确定的想法"。**

**否决 Session 1 的原始措辞**（"任何事实性陈述都必须带出处，缺出处即拒"）。否决理由（引 Pro，成立）：**出处存在 ≠ 出处支持结论**，且假设与推断本来就是探索的正常材料。

### 2.2 我必须补的两处收紧（不补则裁定不可执行）

**(a) 两个责任主体必须分开写，原文把它们挤在一句里。**
机械核验（可自动化，无判断）与实质判断（需要判断，不可自动化）是**两种不同的动作**，混在一句里会导致实现时把"引用能解析"当成"材料支持结论"——这正是第 2 轮把"补丁复验"接成"整体 PASS"（见 §3）的同一种错误。定稿措辞已按此拆成两句。

**(b) `file:line` 单独不构成"固定版本来源"。**
本仓库自己就证明了行号会漂移：计划文件在 `27cdb9c` 被改动 250 行，`p0-scope-ruling.md:27` 记的 §3 行号用的是 `:887/:935`、`gate-round3-pro-findings.md:48` 用的是 `:90–102`——**同一份文档的不同快照**。若把 `file:line` 定为出处标准，产出的是一种**设计上就会腐烂**的格式。
**定稿要求**：固定版本来源 = **commit + 路径 + 版本标识/摘要**（行号可作辅助定位，**不作锚点**）。实测记录 = 命令 + 原始输出 + 采集时间。

## 3. Q3 裁定：失控归因 + 计划/契约节点最小形态

### 3.1 失控归因：采 GPT Pro 版，并把根因钉死

**采 Pro**："不能简单归因于字数或模型档位；更具体的错误是 `gate-round2-fixes.md` §3 把'只复验六处修订'接成了整体 PASS：**补丁复验与整体执行资格不是同一种结论**。"

**同时确认根因已在仓库内记录**：`p0-scope-ruling.md:11` 记 **fix-scope creep**——"每修一个具体缺陷，就把修法普遍化成所有节点都要走的协议"，并指出这才是发动机、散文漂移只是症状。
**核验**：①`gate-round2-fixes.md` §3 的教训**至今未写入该文件**（`p0-scope-ruling.md:63` 明列该更正**待办**）；②fix-scope creep 的三个实例**仍在计划里**：`:626/:650` 的"正文表格行数 == 用例条数"、`:728` 的 `refusalTest`（P-9 四项之一）、`:884` 的 `== 3 + decisions`（此项已在 R3-1 定稿为唯一判据，**保留是对的**，因为成本线必须可判）。

**裁定**：归因以 Pro 版为准，**附加 R1 的 fix-scope creep 为上一级根因**（两者不矛盾：Pro 说的是最近一次误判的形态，R1 说的是反复发生的机制）。

对 Session 1 的 D2 自述（"把 GPT Pro 当校对用、限字数、只问 6 个窄问题"）：该条**无法核验**（见 §6 的 Q5 表），但**不需要核验**——因为 Pro 版归因已经覆盖了它，且可核。

### 3.2 计划/契约作为节点：采 Pro 的六字段最小形态

**采 Pro 原文**（`p0-scope-ruling.md:69` 已记录，表述准确，本裁定确认）：
"应当是普通编排节点，但不应自动成为仓库合并节点。最小形态**复用节点记录**即可：**产物版本或摘要、根任务、审查结论的适用范围、证据指针、未决项、审查轮次**。**不因此强制创建 worktree、租约或 Git 合并意图**；`fault_ref` 约束的是新增机制，不要求每个正常业务任务先找到一次历史事故。"

### 3.3 P0 是否先做该 schema：**不做**——但理由与 Session 1 不同，且有责任附件

**裁定：P0 不建该 schema。** 但不是因为"会变成每个计划都要填的东西"（Session 1 的理由只对了一半，且理由本身已被 R1 自己驳回）。

真正理由（两条，均可核）：

1. **落点本就不在 P0。** 节点记录是 **P2** 的工作项（证据：`plan-0.8.0-execution.md:271` 拓扑图 `[P2: … 节点记录 …]`；`:1009` 把 F1′ 标 P2；`:1049` 的 G-P0 不含节点记录脚本）。**P0 现在建它，就是把一个 P2 的 schema 提前塞进 P0 的范围**——那正是 fix-scope creep 本身。
2. **六字段里五条已经存在，只缺一个标量。** 产物版本/摘要 = 冻结的 `snapshotCommit`/`snapshotTree`（`:726`）；根任务 = 节点记录自身字段；审查结论适用范围 = 审查记录；证据指针 = 证据与 `reuseScope`（`:0.3-R-2`）；未决项 = close 时的 residual（`:197` 附近的 P3-3 ② 口径）。**唯一缺的是"审查轮次"**。

**责任附件（必须遵守，否则本裁定被用来消灭 §4 的裁定）**：

- **"P0 不建 schema" ≠ "轮次计数可以不记"。** 自本裁定起，**计划门与开发平面的每一轮次都以 `docs/` 下的记录文件为准落盘**（轮次编号 + 问题 id + 裁定 + 落点行号）。本裁定自身即示范：§4.3 的核验就是按"同一问题不因换版本清零"口径做的。
- **D3 的六字段在 P2 落地时，`审查轮次`是必填字段**，不得因为"当时没建 schema"而省略。
- 计划里**保留字段名**（Session 1 的建议这部分**采纳**）：`rootTask` / `reviewScope` / `evidenceRefs` / `residuals` / `reviewRounds` / `artifactRef` —— 写成"将产出"口径，不写成已存在（与 `:626` 的"（**将产出**）"同一纪律）。
