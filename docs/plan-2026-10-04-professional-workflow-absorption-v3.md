## 2. 归属与判断

### 2.1 三层归属

TPW 禁止的是"**因为采用它而另造一套运行平台**"，以及"让逻辑路由职责悄悄取得技术设计/并发控制等专业决定权"。它**不**禁止宿主本身拥有 runtime 能力。

| 主体 | 可以承担 | **不因此获得** |
|---|---|---|
| Orchestra 插件代码 | 进程、投递、持久化、恢复、宿主能力适配 | 专业结论的正确性 |
| 承担 Oracle/Driver 职责的 agent | 分派、检查依赖、路由召回、应用既有关闭规则 | B/C/D/F 的实质决定权 |
| 承担 D/E 委托的执行实例 | 设计、实现 Orchestra 的运行机制 | 改写其他责任方的保留承诺 |

**运行支持的存在，不改变各判断的决定责任。** "不建 schema validator" = **不新建通用校验平台**；在既有工具入口校验引用、身份、版本与字段关系，是本来就该做的事。

### 2.2 dispatch 能做什么、不能做什么（R2 修正处）

| **不能**（凭 dispatch 文本做不到） | **可以**（在有效上位委托之内） |
|---|---|
| 凭空取得原委托没有给予的动作许可、接受权、风险接受权 | 选择实例（role / preset / 实际会话） |
| 扩大保留边界、放宽已接受的政策或冻结承诺 | 限定本次工作范围与非目标 |
| 把尚未接受的建议写成"已接受承诺" | 绑定本次适用的方法与 Profile |
| 越过 Owner 明确保留的子系统边界 | 指定交付对象、接收方与关闭规则来源 |

**即：dispatch 在有效上位委托内建立"本次实例绑定"；它记录并落实绑定，但不创造上位授权。** 这不要求每次派发前另建一份内容相同的任务记录——那正是要避免的第二套任务平台。

## 3. 首批范围（收窄）

### 3.1 首批目标（一句话）

> 在**一种受支持的 Session 路径**上，把一次**有真实委托、固定输入与实际方法正文**的派发，可靠地推进到**报告提交、通知恢复与 Driver 后续处理**；故障后**不丢事、不重复派事**。

首批交付的是"**带真实委托的可恢复派发与交接**"，**不是**"实例委托系统"。首批完成时**必须如实声明**：只证明了交接链，**没有**证明该任务已通过独立评价、获准发布或正式关闭。

### 3.2 保留 / 移出

| 方面 | 两周保留 | 移出两周范围 |
|---|---|---|
| 运行载体 | 一个工作区、一个 Team、**Session 后端**；首次懒加载、同一 Session 的后续任务、已保存会话的恢复 | native subagent 的**新增**保证、混合后端、跨工作区、实例丢失后的自动替换 |
| 并发 | 同一 role 同时最多**一个未交付派发**——**首版新增该检查**（`dispatchRoleTask` 当前**没有**任何 in-flight / 未交付 / busy 检查，`src/orchestra.ts:3411-3509`；CAS 只保证写不覆盖，不阻止对同一 role 的第二次派发）。忙时返回明确结果，并配反例 7 | 队列调度器、抢占、一个会话内多个活动委托 |
| 专业内容 | **一个真实 Profile + 少量固定方法正文**（直接使用固定原文，不做消费视图清洗）、真实委托与输入 | 42 篇消费视图、全角色选择目录、章节级加载 |
| 运行闭环 | 派发记录、报告提交、待通知事实、恢复对账、Driver 后续处理、按派发显示未交付工作 | 通用决定命令、委托热修订、完整接受/授权/关闭引擎、传递失效传播 |
| 兼容与恢复 | 新建测试 Team；保留已有路径；**不替旧记录补造授权或完成状态** | 老团队全量迁移、所有历史归档兼容、任意版本在线回滚 |

### 3.3 "只支持 Session"的含义与维度拆分

- **"只支持 Session"是首批新保证的适用范围，不是删除现有 native 功能。** 带新委托契约却走到未支持后端时，必须**明确报不支持**，不能静默退回旧派发然后仍宣称保证成立。
- R2 指出 v2 把两类维度混为"四条路径"。正确表述为：**后端维度**（Session / native subagent）× **生命周期维度**（首次懒加载 / 恢复后继续），两者**组合**。首批只在 `Session × {首次懒加载, 恢复后继续}` 上主张新保证。

## 4. 首批对象：最小可恢复派发集

### 4.1 概念

首批引入的是**本次派发的持久记录**（R2 称"最小可恢复派发集合"），它让运行记录能回答：**谁受托、依据什么、读了哪版输入、要交什么、交到了哪里。**

**不新建一套任务平台**：复用现有 `TeamState`、冻结 Charter、报告存储与 CAS 接缝；不另建 TPW 状态库；不让 Markdown 摘要成为第二状态源。

### 4.2 数据组（首版保留 / 首版不做）

> 下表是**数据职责**，不要求每行新建一种对象或文件。
> **判据（替代 v2 的"只改三处接缝"）**：每个新增字段都要能回答——**谁产生这个事实？哪个当前入口消费它作出什么决定？删除它会失去哪个具体保证？** 答不出来就先放进 brief 或报告，不做结构化。

| 数据组 | 首版保留 | 首版不做 |
|---|---|---|
| 派发身份 | `dispatchId`（**调用方显式提供**）、**工具按约定输入字段计算的** `payloadDigest`、固定 `bindingRevision = 1`；team 身份取自当前上下文 | 通用委托版本编辑器 |
| 实际主体 | 发起 Session、目标 role、**materialize 之后的实际 Session**、结果接收方；**主体身份由运行时记录** | 仅凭模型填写的 `recordedBy` / `author` 就采信 |
| 委托依据 | 精确的 `charterRef` / `authorityRef`、本次责任、授权内的工作范围（两者可指向同一既有来源，不重复建账） | 通用授权继承／风险取舍引擎 |
| 启动内容 | **一份持久、固定的 brief**，承载六项基线及必要引用 | 把目标、非目标、每个事实、每条限制都拆成独立记录 |
| 实际输入 | 本次消费的对象、**固定版本**及用途；重要输入不能只有 mutable branch 名 | 全仓对象注册表 |
| Profile 与方法 | `profileRef`（选定 Profile 的固定正文与来源）；**少量** `methodBindings`，携带固定来源与实际内容身份 | 全量自动选择、章节裁切器、运行中切换包版本 |
| 结果 | `reportId`、`dispatchId`/`bindingRevision`、实际提交实例、不可变正文引用/digest、**结果或阻断**类型 | 把任意 report 都升级为接受／授权／关闭决定 |
| 交付恢复 | 投递状态、报告对应的待通知事实、实际目标及回执；`unknown` **明确保留** | 跨后端、任意任务的 exactly-once 承诺 |

**同一事实只能有一处可写归属**（R2 要求）：`inputRefs` 与 `consumes`、报告内的召回与 `recalls[]`、正文中的决定与 `decisions[]`，首版先确定唯一归属，其余只能是引用或派生视图。

**两个字段的消费者裁定（Reviewer，开放项 1）**：

| 字段 | 裁定 |
|---|---|
| `bindingRevision`（固定 1） | **可留，但必须在实现与文档中标注"首批无消费者、为第二批预留占位，不得用于宣称任何首批保证"**。首版报告关联只用 `dispatchId` 即可成立。 |
| `applicabilityBasisRef` | **移出首版最小形状**（首版没有政策/承诺校验引擎消费它），属第二批语义。 |

其余字段消费者成立：`dispatchId`/`payloadDigest` → dispatch 入口的去重/冲突判定；主体身份 → §7.1 反例 5/6 与归档；`charterRef/authorityRef` → §7.1 末段承诺的"引用无效即拒派"；`profileRef`/`methodBindings` → §7.2"方法正文真到达 worker"的硬验收；结果组 → §3.2"按派发显示未交付工作"与反例 6；交付恢复组 → §5.4 三条恢复入口。

### 4.3 不可变与更新规则（R2 要求补齐）

- **初始委托不可变，`bindingRevision` 固定为 1；首版不实现原位修订协议。**
- **执行中补读**：在现有委托内追加阅读，只记录"本次另外读取了哪个固定版本的方法、用途是什么"，**不改写初始 payload**。它不是授权变化，**也不需要每读一个 guide 就生成新版本**。
- **实质变更**（目标、必须保持的承诺、决定责任、动作范围）→ 建立**明确关联前项的新派发**；旧派发保留其处置结果。
- **新 ID 不能用来伪装重试**，也不能清空原任务的贡献、未完成项或评价历史。

### 4.4 六项基线：一份固定 brief

R2 修正："**能够解析**"不等于"全部必须是机器结构化引用"。

| TPW 启动基线 | 首版形态 |
|---|---|
| Goal | brief 中的目标 / 非目标；与原任务是新目标还是 steering |
| Known facts | brief 中的事实／假设／未知**及其来源** |
| Behaviors that must not change | `preserveRefs`：具体承诺、版本、决定责任 |
| Fixed inputs | `inputRefs`：实际消费对象的 commit / revision / artifact identity |
| Observation and closure | 需要评价的 claim、观察方式、评价责任、**关闭规则引用** |
| Write surface | 预计改动面、**实际授权面**、明确禁令、共享写者与整合点——**分别表达** |

**预计触及的文件集合 ≠ 实际权限边界。** 只有运行时确实要据此**比较、定位、拒绝或恢复**的部分才做机器字段；其余可以是 brief 里清楚的文字 + 已有契约引用。TPW 自己允许"没有既有治理的任务只补一段任务简述 + 一份 Charter"。

D 类委托还应能解析出 **Commitments / Delegated Decisions / Recall Conditions**（可引用同一份 Plan，不复制成另一张表）。

### 4.5 Profile 与方法的取得（v2 漏项）

v2 承诺六个 Profile 的心智模型按需加载，却没有取得通路——`judgmentCapabilities[]` 不是 Profile 正文，`judgmentFunctions[]` 也不是。

- **首版：派发时携带选定 Profile 的固定正文及来源**；方法再走既有按需读取通路。符合 TPW 的 `Profile → 必要 authority → Charter → 方法 → 任务输入` 装配顺序。
- **不为此增加六个稳定角色或六个工具。**
- 方法绑定的最小形状：

```text
methodBindings:
  - methodId
  - sourceCommit
  - contentDigest        # 见 §8.2：须区分"来源身份"与"实际送入实例的内容身份"
  - purpose
  - sections             # 需要时
  - applicabilityBasisRef    # 有既定政策/承诺要求时
```

**绑定了，不证明已读到；读到了，不证明已按方法完成；按方法完成了，也不证明专业结论正确。**

### 4.6 三条边界

1. **`authorityRef` 必须能回到真实委托或接受记录。** 模型填写"Owner 已批准"不是授权事实。Orchestra 已有绑定确切 draft revision、digest 与真实用户回复/命令来源的批准记录，沿用该来源纪律。
2. **新授权字段不能只加到 `FrozenCharterRevision`。** 当前 `digestPayload()` 只纳入既定的 draft 身份、base、mission、topology 与 human participation policy；**只给 Frozen 类型加字段，不会自动使其成为用户批准过的内容**。要成为批准依据，必须同时进入：草稿内容 → 用户看到的提议 → digest → approval 绑定 → freeze → 恢复读取。
   **两周首版优先引用现有真实批准对象**，不一次引入多类新的 Charter 权力字段；确实新增**一项**机器消费的授权字段，就把该项的完整批准链做完；没有来源或无法解析的部分**保持未决，不能自动填成允许**。
3. **复用 `decisions[]` 的存储位置 ≠ 假设旧 `orchestra_decision` 工具还在。** 新写入必须接到当前支持的入口，并在分支上检查真实调用者与授权来源，而不是解析 Markdown 里的"批准"二字。

## 5. 派发与投递的保证

### 5.1 身份（R2 修正处）

- **受可靠性保证的派发必须显式提供 `dispatchId`，且发起方在首次调用前就持有它。** 不增加"先申请 ID"的新工具——直接作为调用参数。
- 便利性的**默认铸造首版不提供**；若将来提供，**不得与上述可靠路径宣称同等保证**。
- `payloadDigest` 由**工具**根据约定的输入字段计算，**不接受调用者自报**。
- **同 ID 首次调用并发到达时，检查与创建必须经过同一个原子状态变更**；否则"先查无记录、再创建"仍可能产生重复事实。
- 语义：**同 ID 同内容 → 复用既有记录；同 ID 不同内容 → 明确冲突；新 ID → 合法新意图**（即使任务文字完全相同）。
- **投递必须携带幂等凭据**（Reviewer 必改 3）：`dispatchRoleTask` 当前调 `deliverMessage` **未传 `idempotencyKey`**（`src/orchestra.ts:3496-3499`），而 `recordReceipt` 只在传 key 时写、无 key 时连去重都不做（`a2a-transport.ts:413-414`）⇒ **当前 dispatch 投递不落任何回执**。受保证的派发投递必须带上幂等凭据（`dispatchId` 同值或由其派生）+ `receiptStore`，否则 §5.2 保证 #2 的"已确认投递"**没有任何可判定的证据来源**。

### 5.2 保证等级（R2 修正处）

v2 把"只发生一次逻辑执行"写成保证，但它没有定义接收端在哪里认领任务、恢复时怎么判断是否已开始、不确定时是否允许再次向模型投递正文。**这是源码顺序支持的风险，不是 `payloadDigest` 能消除的。**

首版保证写成：

> 1. 一次意图只有**一个派发记录**；
> 2. **已确认投递**的重试复用既有结果——"已确认投递"= 该次投递**留下了可查询的持久凭据**（§5.1 的幂等凭据 + receiptStore）；没有凭据时不得声称本条成立；
> 3. 投递结果**不确定**时，先对账，**不自动重新派发工作**；
> 4. 报告与通知按其**稳定身份**恢复；
> 5. **首版不承诺**任意 agent 工作或外部效果恰好一次。

**必须分开两种重试**：

| | 通知重试 | 任务重试 |
|---|---|---|
| 语义 | 告诉 Driver"报告 R 已存在" | 要求 worker **再做一次工作** |
| 首版 | 可围绕同一事实恢复 | **效果未知时不照搬前者的策略** |

取得接收端真实执行入口并能在那里去重之后，才增加"同一派发不重复启动"的保证。

### 5.3 交接判据与 turn-stop 解耦（R2 修正处）

`tool/result.isError === false` 是**必要改进，不是完整定义**。至少建立：**本次 dispatch → 本次产物／明确阻断 → 对应接收方 → 已持久化或已接受投递的事实**。普通协调消息**不能**替代交付；结构化业务失败也不一定表现为 `isError=true`。

但它**不能**直接作为"worker 是否可以结束 turn"的唯一条件。反例：报告已持久提交、待通知事实已可靠登记，只是 **Driver 暂时不可达**——此时若仍判"未交接"并继续 steer，就会重新引入重复生产。拆成三个独立判定：

| 判断 | 成立条件 | 谁负责后续 |
|---|---|---|
| worker 已履行本次提交责任 | 本次结果或明确阻断**已持久提交**，通知责任已被运行时接管 | 运行时 |
| 接收端已接受通知 | 有对应投递事实 | Driver |
| Driver 已处理结果 | 有其实际读取、回应或后续安排的证据 | Driver |

**工具返回失败也不一定等于报告未提交。** 提交后渲染或返回阶段出错时，应先读取**已提交事实**，而不是仅凭 `isError` 决定重做。

当前报告工具是"先写文件、再改团队状态、最后通知"，因此首批必须**明确报告的提交点**，并让"报告索引 + 待通知事实"进入**同一次 `TeamState` 变更**；文件已存在但索引未提交的情况，要有明确对账路径。**不宣称它因此变成了跨文件事务。**

**提交点（Reviewer 裁定，开放项 2）**：提交点 = `orchestra_report` 里那次**成功的 `activeTeamState.mutate` CAS**（`src/orchestra.ts:5230-5266`），**不是** `ctx.fs.writeText`（`:5226`）。理由：
(a) `reportId`、`reports[]`、`role.reportCount/lastReport` 与首版新增的"待通知事实"必须在**同一次变更**内原子的可见/不可见；
(b) 崩溃发生在两步之间时，对账路径**天然幂等**——以同一 `path + content` 重放会算出同一 `reportId`，被 `:5238` 的去重拦下，不会双计。

**注意（Reviewer 建议 4）**：`reportId = sha256(teamId:role.id:canonical:contentHash)`（`:5235-5240`）只保证**账目不重复**；报告文件本身是**无条件覆写**（`:5226`，无 CAS）。"已提交事实保留"**不等于"文件字节不被改写"**。若要承诺后者，需在报告中记录 `contentHash` 并在覆写前比对。

### 5.4 通知恢复

- 需要**明确触发条件**的待投递记录：运行期**有界重试** + **启动时重新接续** + **接收方恢复时对账**。复用现有插件生命周期与定时能力，**不需要新服务**。
- `noticeFailures` 保持诊断身份：有上限、存的是失败说明。**未完成的待办不能因为超过 20 条就消失**——诊断记录与待交接事实**分开**。

## 6. 后续批次与运行语义目标

> 本节语义**不在首批交付**；列出是为了让首批接口为它们留位，并让后续批次有明确归属。

### 6.1 第二批：评价、接受、召回、关闭接到当前工具契约

- 先支持两个有区分力的任务：**已有契约的局部修复**（复用已有 A–D，只调必要 E/F，不强制加 architect 或设计 gate）；**新增共享承诺的变化**（明确 B/C/D 的决定对象、设计挑战与实现后评价；上游语义问题只召回相关依赖）。
- 在 `orchestra_report` 等**当前入口**上承载结构化事实与有效处置。**不恢复那 16 个微状态机工具**，也不把 Driver 变成逐节点填表的人。
- 第二批再补**两项真正有消费意义的字段**：**评价依据引用**（仅有 `subjectVersion + claim + evidence` 不够，还要知道"正确预期来自哪个已接受版本"）；**贡献关系的来源**（"不同 session"或自报的贡献列表不能自动升级为独立性证明，**不要用一个 `independent: true` 把语义压扁**）。

### 6.2 四态是四种独立事实，不是四阶段状态机

**不要**实现成 `accepted → verified → authorized → closed`。

| 事实 | 必须回答 | **绝不能**自动推出 |
|---|---|---|
| 约定接受 | 哪个约定版本，由谁依据什么委托接受 | 已实现、已验证 |
| 证据评价 | 哪个 claim、对象版本与覆盖，有何证据 | 动作许可、风险接受 |
| 动作授权 | 哪个主体，可对哪些对象产生哪些效果 | 方案正确、结果成立 |
| 委托关闭 | 哪个委托，依据哪条规则及哪些事实关闭 | 已部署、用户价值已实现 |

**同名陷阱**：A2A 的 `state: accepted` 只是**投递接收**，不是 TPW 的 contract acceptance。工具输出与状态展示必须把两者放在不同语义域。

### 6.3 三态判定与阻塞/未知分离

新的评价记录采用 **PASS / FAIL / UNVERIFIED** 并绑定具体 claim：`FAIL` = 有效观察反驳了预期；`UNVERIFIED` = 证据不足、观察无效或环境阻止结论；`PASS` = 证据在声明的对象、条件与覆盖内支持预期。
`BLOCKED` 继续作为**工作推进状态**；外部动作的 `unknown` 作为**效果待对账**的执行状态。**尚未进行评价，不能伪装成"F 已经给出了 UNVERIFIED"。**

### 6.4 独立性绑定对象与贡献

评价记录至少说明：`subjectRef/subjectVersion`、`evaluatorInstanceId`、`authorOrContributorRefs`、`evaluationKind(design-challenge | implementation-evaluation)`、`coverage/observationTime`。
**同一实例换个 role label 不能登记为独立评价者**；**不同 session ID 也不自动证明独立性**；正常质疑、反例与补证要求**不能一律算成作者贡献**。贡献记录不能被恢复、换名、换模型或替换实例清空。

### 6.5 召回：明确标记 + 继续前拦截（首批范围内的小切片）

R2 的裁定：**首版做"明确范围的标记 + 继续前拦截"，不做纯提示，也不做自动杀进程或全图传递。**

三条区分：**提出问题 ≠ 有权撤销结论；新版本 ≠ 旧版本全部失效；挂起推进 ≠ 立即中断执行。**

首版行为：对**已明确列出的直接依赖**，记录"需重新确认"及原因；Orchestra 在**下一次受控派发／继续／结果采用入口**阻止越过该条件；已在执行的实例收到明确通知，在安全边界返回；**晚到报告仍保存，不能自动满足新依据**；不自动取消关键写入，不宣称能阻止工具外所有效果。

**拦截入口清单（Reviewer 裁定，开放项 3）**：首版**只声称两个真实入口**——
1. `orchestra_dispatch`（受控派发）：在目标/引用解析时检查 hold 条件；
2. turn-stop steer 文本：对"继续"给出显式提示。

"结果采用"**目前没有对应工具入口，不要为它新造工具**；应定义为"后续派发的 brief 引用了被 hold 的结论/报告"这一**引用检查**，落在 `orchestra_dispatch` 的解析里。清单加上这条定义才算完整。

首版不做传递闭包时，**Driver 必须明确处置可能受影响的后续链**——**不能把"没有自动遍历到"当作"已证明不受影响"**。无关车道继续工作。以 `consumes[]` 为输入的自动定向传播留在第二批。

### 6.6 归档 ≠ 关闭

`dismissGovernedTeam` 按角色累计 `reportCount` 判 pendingTasks，**角色累计报告数不能代表当前任务完成**。增加派发记录后，归档/恢复应按**本次委托状态**重建未完成工作。
`orchestra_dismiss` 继续负责停止与归档，**不因专业验收未完成就不能停团队**；归档记录"已关闭 / 未关闭 / 放弃 / 待恢复"的真实情况；**archive 不是 completed 的另一种拼写**。

### 6.7 诚实限定保证范围

这些改动能让 Orchestra 在**自己控制的入口**上保护身份、版本、接受来源、独立性条件、召回与关闭资格。它们**不会**自动限制一个仍持有广泛 Bash 权限的 agent 在工具外产生的所有效果。**方法绑定不是沙箱，`authorityRef` 也不是沙箱。** 产品声明必须区分：**"编排契约不允许继续"** 与 **"宿主已强制阻止该效果"**。

## 7. 验收

### 7.1 首批六组反例（实现方须逐条证明）

| # | 反例 | 必须观察到的结果 |
|---|---|---|
| 1 | 同 ID 同内容重试；同 ID 不同内容；不同 ID 相同文字 | 复用原记录 / 明确冲突 / 合法新意图 |
| 2 | 派发已入队但回执写入失败 | 不盲目创建新任务；能对账则恢复，不能则显式 `unknown` |
| 3 | 报告文件／索引／通知之间发生故障，并重启 | 已提交事实保留；未完成步骤可定位；**worker 不因通知失败重新生产报告** |
| 4 | 只发一条进度消息，或报告调用失败 | **不能被误判为本次有效提交**；已成功提交但通知待处理时**不反复 steer** |
| 5 | 其他实例冒报该 dispatch，或旧派发结果试图满足新任务 | 身份／绑定不匹配**不能**完成当前任务；历史结果仍可保留 |
| 6 | 同一 role 旧任务有报告、新任务没交付，再归档／恢复 | 新任务仍显示未交付；**归档不被显示为专业关闭** |
| 7 | 对**已有未交付派发**的 role 再次派发（必改 1 的首版新增检查） | 返回**明确结果**（拒绝或排队），不得静默产生第二份未交付派发；该检查**是首版新增**，不是"现有机制" |

**首批反例的证明边界（Reviewer Q4 要求写进验收说明）**：反例 2/3 即使 worker 上下文里收到两份相同派发正文也照样会绿——§5.2 已明确不承诺"不重复启动"，所以这不构成缺陷，但**首批反例只证明"不盲目创建新派发记录"与"不重复记账"，不证明"worker 不重复收到消息"**。实施方与报告读者不得把绿灯读成更强结论。另：反例 3 的"已提交事实保留"按 §5.3 的说明理解——**账目不重复 ≠ 文件字节不被改写**。

"工具可写但无动作授权"在首批**只能声称实际实现的那部分**：例如缺少有效引用、引用错误 Team、调用主体不符时拒绝派发。**不能借该测试宣称已经理解并强制执行任意自然语言授权边界。**

### 7.2 首批必须演示的完整交接链

选择一个**已有行为约定的、有界局部任务**，串起：

> 真实批准并创建 Team → Driver 派发固定委托 → Session worker **实际取得 Profile／方法** → 提交本次结果或明确阻断 → 运行时保存报告及待通知事实 → Driver 被通知并读取该报告 → **重启后仍能定位同一份委托与未完成步骤** → 给出明确后续安排。

**演示任务的筛选条件（Reviewer 裁定，开放项 4）**：
1. 输入可固定为**单一 commit/SHA + 一个确定性失败观测**（不用需要新鲜外部信息的任务）；
2. 方法正文用 TPW **`local-defect-feedback-loop.md` 固定原文**（同时满足 §8.6"不清洗也先跑通真实取用"）；
3. 验收信号是**可复现的 fail→pass 输出**；
4. **不要**选需要 web 或外部副作用的任务——那会把首批拖进未支持后端。

**方法内容必须真的到达 worker。** 不能把所有"方法取用"都推到第三批，同时又说首批演示了 TPW 方法运行——**首批可直接使用固定原文，不做消费视图清洗**。

演示结束必须如实说明：**它只证明交接，没有证明整个任务已通过独立评价或获准发布。**

### 7.3 第二批才主张的语义（不要在首批验收里用）

跨后端 exactly-once；完整接受／授权／关闭引擎；传递失效传播；独立性判定的完整实现；`decisions[]` 的新语义与通用整合权。首批只需为它们留出接口位置。

### 7.4 关于 §12（测试环境）证据的界限

§12 记录的是**某次真实模型调用 `a2a_list` 成功**——它**不能**证明建队、懒加载、报告、重启恢复这条路线可用。**第一段实施工作就应触碰这条真实路线**，而不是等字段都写完再测试宿主。

### 8.3 包内引用必须可解析

"句中文字不动"不够：**文件文字不变、引用目标失踪，消费语义一样会坏。** 方法正文会引用 `charters/README.md`、其他 guide 或方法；只输出扁平 `methods/<slug>.md` 时，必须说明这些引用**怎样解析**。

但**引用检查不能把历史出处都当成运行依赖**：实际使用的方法、条件与必要 Profile 指针必须可达；**包外历史验收记录、可选例子不应一律触发"缺文件就拒绝使用"**（TPW 的 ADOPTION 明确允许只 vendor core）。

### 8.4 统一 header（v2 已改，v3 保留）

> 本文提供判断方法，**不因被选择或加载而产生接受、权限或门禁**。
> 本次适用性与动作边界来自**所引用的有效委托、政策与已接受承诺**；dispatch **记录**这些绑定，**不自行创造**它们。
> **工具能力与动作授权必须分别满足。**
> 发现冲突或缺失的关键判断时，说明受影响对象、事实及影响，返回**拥有该决定权**的责任方；**只暂停依赖该问题的工作**。

### 8.5 绑定 ≠ 封闭

- **初始绑定**：Driver 指定首先需要的方法与原因。
- **执行中补充**：实例在已有委托内补充所需方法并记录用途；涉及新增判断责任或改变承诺时，再召回相应责任方。**追加阅读不等于追加权限。**
- **"一篇文件"不是最细的适用单位**：`interface-contract-and-retry` 明确把接口契约与重试语义分成可独立选择的部分。方法绑定可带 `sections`/`purpose`，但**不据此建立新的知识图谱**。

### 8.6 skill 注册与索引

- 名字 `pw-<slug>`；`description` 取选择表的**任务触发语**；**不做单值 judgment 机械提取**。
- 注册集合 = **42 篇方法 + 2 个辅助 skill（`pw-method-index`、`pw-responsibility-backbone`）**，**分开计数**。
- 摄取器硬性失败条件：无写死 commit、表与文件非 1:1、`Source anchors` 不是末节、`--verify` digest 不符、**承重引用目标缺失**。
- **首批只做只读跑测**（并行、不当前置），回答三个问题：固定版本中的实际文件与入口是否一致；选定方法的承重引用能否被接收实例解析；v3 的变换会不会删掉适用条件或改变实际加载身份。**不必在首批期间完成生产摄取器与 42 篇注册。**
