# P0 开工范围裁定（Pro 第 3 轮结论 → 一轮修订 → 开工）

> **来源**：ChatGPT Pro 对冻结契约 v1.2.1 + 执行计划的第 3 轮判断（基线 `27cdb9c`，未跑项目测试；恢复表部分在独立临时 git 仓库构造反例）。
> **主结论（原话要点）**：**可以开始 P0，但应停止把"证明整个 0.8.0 计划完备"作为开工前提。现在最危险的不是交付闸严格，而是每修正一个问题，就把修正办法扩张成所有节点都必须经过的新协议。**
> **本文件的作用**：把它的判断翻译成**一轮修订的具体改动**。改完即开工，不再整轮复审。

## 0. 根因修正（比我原来的 H1–H4 更本质）

**真正的机制是"修订范围蔓延"（fix-scope creep）**：每修一个具体缺陷，就把修法**普遍化**成所有节点都要走的协议——§5 的"表格行数 = 用例条数"、§6 的"每条决策记录都带 `refusalTest`"、§9 的"每轮恰好 3 + decisions 次"。它反过来**制造交叉引用**，于是又产生旧文本失配——**我诊断的 H1（散文漂移）是症状，这一条是发动机。**

H1–H4 的修正版（采纳 Pro 的判断）：
- **H1 成立**，但**把事实搬进 JSON 只消除副本漂移，不消除错误规则**；§5 那条"行数 = 条数"正是**把错误的一致性代理指标机械化了**（条数相等 ≠ 覆盖了不同分支）。
- **H2 改述**：不是"先把整个系统调查完才许写计划"，而是「**依赖某项事实作出不可轻易撤销的设计决定之前，先验证该事实**」（针对性探针：预设挂载、恢复入口、权限策略）。
- **H3 收窄（我原来那条太粗暴）**：**出处存在 ≠ 出处支持结论**；假设与推断是探索的正常材料。结构约束只作用于「**将被升级为执行依据的关键事实**」：在报告提交 / 任务派发 / 方案采纳入口，绑定「陈述 — 固定版本来源或实测记录 — 适用范围」；宿主检查引用能否解析、版本是否匹配、实测记录是否存在；**独立审查者判断材料是否支持结论**。无证据不得升级为"已验证前提"，但**可以明确标成假设并授权一次有界探针**——拒绝的是**无证据地授予资格**，不是说出一个不确定的想法。
- **H4 修正**：不是字数或模型档位的问题，具体错误是 `gate-round2-fixes.md` §3 **把"只复验六处修订"接成了整体 PASS**——**补丁复验与整体执行资格不是同一种结论**。

## 2. 现在必须钉死的四件事（其余留到实现中定）

1. **证据绑定哪个版本**；2. **哪些记录不可改写**；3. **哪些动作确已发生**；4. **谁有权授予资格**。
其余（后续字段、脚本、报告细节）**在实现中确定**，不必现在补齐。五节报告保留为**后续报告契约**，不得成为"没有治理数据也要填满"的当前任务。

## 3. 我的补充：一条防"修订范围蔓延"的规则（建议写进契约 §0/元规则旁）

> **R-creep**：**每条修订必须写明它作用的节点类型与适用边界；不得因一个实例把义务推广到所有节点。**超出原实例范围的普遍化，必须作为**独立条目**重新过一遍元规则一（指得出一个已付过成本的故障）与"相对已有覆盖增加了什么"。

理由：元规则一和每周复查只约束**新机制准入**，**不约束"把一个修法扩张成通用协议"**——而本次失控正是后者。这条不新增产品机制，只给修订加一道边界声明。

## 4. P2 启用门（现在不改，但必须在 P2 前修掉）

**B5 的成功判定是错的**（Pro 在独立临时 git 仓库构造了反例）：B5 判的是 `candidateCommit` 是否当前 ref 的祖先，然后宣告"A 已成功"——但**候选提交被另一条历史包含，不证明这次 attempt 的 `expectedNew` 已进入目标历史**。反例：从同一基线 O 与候选 C，创建计划的合并提交 M，以及另一个包含 C 的提交 B；只把目标分支推进到 B、**从未安装 M** ⇒ `C 是 B 的祖先` 退出码 0、`M 是 B 的祖先` 退出码 1 ⇒ 现表会走 B5，把**未完成**的 attempt 记成成功。它还观察到恢复时把 ref 写回 `expectedNew`，**进一步改写了这次 attempt 原本要产生的效果**。
⇒ **必须用不可变的 `expectedNew` 判断"这次精确提交是否已进入历史"；恢复观察到的后继值另记，不得替换 `expectedNew`。**

另三处（同样 P2 前必修）：
- **祖先判定不是二值**：`--is-ancestor` 0=是、1=否、**其它非零=错误**（构造缺失对象得到 128）⇒ 必须进**不可判定并阻断**，不得当"不是祖先"后重新预演；
- **"第三个值且不含本次提交" ≠ "合法前进"**：还要确认它相对 `expectedOld` 是**允许的前进**（回退/分叉/对象不可读不能都走 `base_advanced`），且**先把 ref 解析成固定 OID** 再比较；
- **控制流自相冲突**：A1 说"不存在即返回"、B6 却说接收 A1；阶段 B 说"命中即停"、B2 却要求继续 ⇒ **收成一个实际判定函数**（输入校验 / 成功记录校验 / 效果核对 / 未执行分支 / 不可判定分支），**用反例驱动**，不再用"每行一个用例、条数相等"宣称完备。

## 5. 档 0 补充（三组边界 + 两项检查）

1. **无 Git / 交付服务不可用时，两个会话仍能通信**，且不触发交付存储、报告、检查；
2. **纯聊天引用 commit、文件路径或研究报告不触发准入**——**正式采纳为执行依据才触发**；
3. **档 0 跨重启保持关闭**；首次交付请求**在效果发生前重新准入**，失败时**没有半份交付状态**，旁边聊天会话不受影响。
4. 检查**交付工具的 schema 是否被无条件塞进纯聊天上下文**——"没有调用"≠"没有上下文成本"。
5. 第五条反向用例要限定：**裸标签不能强加流程成本，但"经过授权的交付准备/派发请求"不是裸标签**——要区分「**描述自己是什么**」与「**请求系统做什么**」，不是再加语义分类器。

## 6. 对我们自己文档的四处更正（一并改掉）

1. `docs/explainer-delivery-layer.md` §三"机器变厚、不消耗任何模型上下文"**不成立**：要求模型准备更多字段、解释更多拒绝、处理更多失效，**即使判定代码在宿主侧，仍增加模型工作；工具调用数不是全部摩擦**。
2. `docs/gate-round2-fixes.md` §3 的教训要写明：**补丁复验 ≠ 整体执行资格**，不得由局部复验接出整体 PASS。
3. **"散文没有版本所以不会发生'旧结论被挪到新代码上'"是错的**——**散文有版本，审过旧计划却执行新计划同样会出事**；要保留的是**版本绑定**，不是把整套代码交付流程移植过来。
4. **计划/契约节点自身实现量为零，不能据此判定浪费**——配比要**归到根任务**；并且 **P4 的仪表目前仍是待实现工作**，不能把"设计了自我纠偏能力"当成"这次已经有能力自动阻止循环"。

## 7. 计划/契约作为节点的最小形态（不新增负担）

**应当是普通编排节点，但不应自动成为仓库合并节点。** 最小形态**复用节点记录**即可：产物版本或摘要、根任务、审查结论的**适用范围**、证据指针、未决项、审查轮次。**不因此强制创建 worktree、租约或 Git 合并意图**；`fault_ref` 约束的是**新增机制**，**不要求每个正常业务任务先找到一次历史事故**。
