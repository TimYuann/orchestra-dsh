## 2. 归属与判断

### 2.1 三层归属（替代 v1 的"冲突"表述）

TPW 禁止的是"**因为采用它而另造一套运行平台**"，以及"让逻辑路由职责悄悄取得技术设计/并发控制等专业决定权"。它**不**禁止宿主本身拥有 runtime 能力。三个主体各承担什么、不因此获得什么：

| 主体 | 可以承担 | **不因此获得** |
|---|---|---|
| Orchestra 插件代码 | 进程、投递、持久化、恢复、宿主能力适配 | 专业结论的正确性 |
| 当前承担 Driver 职责的 agent | 分派、检查依赖、路由召回、应用既有关闭规则 | B/C/D/F 的实质决定权 |
| 承担 D/E 委托的开发实例 | 设计、实现 Orchestra 的运行机制 | 改写其他责任方的保留承诺 |

**运行支持的存在，不改变各判断的决定责任。** 同理："不建 schema validator" = **不新建通用校验平台**；在**既有工具入口**校验引用、身份、版本与字段关系，是本来就该做的事，不属于被排除的范围。

### 2.2 拿什么、不拿什么

| TPW 资产 | 处置 |
|---|---|
| A–F 责任接口、Voice/Driver、四态分离、召回语法 | 吸收为**语义**，并落到 `§4` 的实例委托与 `§5` 的运行对象 |
| 6 个 Profile 的心智模型/误区/召回 | 吸收为**判断心智模型正文**（按需加载），**不**做成固定岗位映射 |
| 42 篇方法正文 | 保留**固定版本来源副本**；日常加载**机械生成的消费视图**（`§8`） |
| `methods/README.md` 选择表 | 只取"任务触发语"作为 skill 的 `description`；不做单值 judgment 提取 |
| Instance Charter 六项 | 落成**引用解析**，不是六个自由文本标签（`§4.3`） |
| Backbone 全文 | 只读参考正文，供权责争议时查 |
| Status / 验收 / 来源锚点 / 外部 pin | **保留在来源副本**，不送入日常上下文 |
| 旧版 registry/roles/skills 体系 | 不涉及 |

## 3. 核心：实例委托（Instance Delegation）

> 这是 v1 缺失的那一层，也是评审认定"最该先做"的对象。**不新建一套任务平台**：复用现有 `TeamState`、冻结 Charter、报告存储与 CAS 接缝，不另建 TPW 状态库，不让 Markdown 摘要成为第二状态源。

### 3.1 为什么需要它

现在运行记录能回答"哪个角色写过几份报告"，**不能**回答：本次实例受谁委托、对哪个版本的对象承担哪类判断、依赖哪些已接受结论、可以改变什么、结论变化后哪些工作不得继续。没有这层，"方法送进上下文"只是把措辞变得更专业。

### 3.2 对象与字段（设计建议，不是当前已有能力）

| 现有对象 / 文件 | 建议增加 | 为什么 |
|---|---|---|
| `RolePresetSpec`（`orchestra-role-presets.ts`） | `judgmentCapabilities[]`、`concerns[]`、`chooseWhen`、`decideNot`；方法默认值仅作**选择建议** | 描述"适合承担什么"，不把岗位名称变成权限 |
| `FrozenCharterRevision`（`orchestration-charter.ts`） | 可引用的 `delegationRefs`、保留决定、动作边界、`integrationAuthorityRef`、`closureRuleRef` | 把任务级授权来源与取舍/关闭责任落到**已批准对象**，不靠每次 dispatch 自述 |
| `TeamState.dispatches[dispatchId]`（`orchestra-state.ts`） | `bindingRevision`、`charterRef`、任务/目标关系、实际接收实例、输入版本、责任绑定、方法绑定、投递状态 | 同一角色可执行多个任务；任务级身份才能恢复、去重、召回 |
| `TeamState.reports[]` + `orchestra_report` | `dispatchId`、`bindingRevision`、不可变正文引用/digest、`kind`、被报告对象/版本；评价报告携带 `claim` 与 `evidence` | 报告不能只有路径与角色累计计数；进度/交付/评价/召回不是一种事实 |
| `OrchestrationDocument.decisions[]` | 区分**接受 / 动作授权 / 关闭 / 召回处置**；记录 `decisionOwner`、`recordedBy`、`authorityRef`、对象/版本与依据 | Driver 可以**代记录**决定，但"记录者"不能自动成为"决定者" |
| 委托记录 | `consumes[]`（消费了哪些结论/版本）、`recalls[]`（涉及哪个结论、事实、影响、去向、处置依据） | 实现**定向失效与定向暂停**，不靠全团队重开 |
| Team 内待通知记录 | `noticeId`、来源事实 ID、目标实例、投递回执、待处理状态 | 通知围绕**同一业务事实**恢复，不让 worker 重复交付来补通知 |

### 3.3 两条必须守住的边界

1. **`authorityRef` 必须能回到真实委托或接受记录。** 模型填写"Owner 已批准"不是授权事实。Orchestra 已有绑定确切 draft revision、digest 与真实用户回复/命令来源的批准记录，沿用这种来源纪律。
2. **复用 `decisions[]` 的存储位置 ≠ 假设旧 `orchestra_decision` 工具还在。** 新写入必须明确接到**当前支持**的入口（例如扩展 `orchestra_report` 的结构化类型），并在分支上检查真实调用者与授权来源，而不是解析 Markdown 里的"批准"二字。

### 3.4 六项基线怎么落下去（主要通过引用解析）

| TPW 启动基线 | 实例绑定中的实际内容 |
|---|---|
| Goal | 本任务目标、非目标；与原任务是新目标还是 steering |
| Known facts | 当前依赖的事实/假设/未知**及其来源** |
| Behaviors that must not change | `preserveRefs`：具体承诺、版本、决定责任 |
| Fixed inputs | `inputRefs`：实际消费对象的 commit / revision / artifact identity |
| Observation and closure | 需要评价的 claim、观察方式、评价责任、**关闭规则引用** |
| Write surface | 预计改动面、实际授权面、明确禁令、共享写者与整合点——**分别表达** |

**预计触及的文件集合 ≠ 实际权限边界。** 否则新增一个合理的内部 helper 会被误当越权，而真正禁止的数据库或外部效果可能藏在泛化的 "workspace-write" 下面。

D 类委托还应能解析出 **Commitments / Delegated Decisions / Recall Conditions**（可引用同一份 Plan，不必复制成另一张表）。否则给 implementer 的仍是"执行这个计划"，而不是"哪些必须保持、哪些可以自主选择、什么变化必须返回"。

### 3.5 方法绑定的最小形状

```text
methodBindings:
  - methodId
  - sourceCommit
  - contentDigest
  - purpose
  - sections            # 需要时
  - applicabilityBasisRef   # 有既定政策/承诺要求时
```

与"skill 注册名"不同：注册名解决**发现**，commit/digest 解决**本次使用哪一版**，purpose/sections 解决**为什么使用、用到哪里**。

**绑定了，不证明已读到；读到了，不证明已按方法完成；按方法完成了，也不证明专业结论正确。** 因此 `verifier` 改 `skills:true` 是必要修复，但**不能**当作 F 能力已成立的证据。

## 4. 必须由运行时保护的语义

### 4.1 四态是四种独立事实，不是四阶段状态机

**不要**实现成 `accepted → verified → authorized → closed`（TPW 没有要求固定顺序）。按对象分别记录：

| 事实 | 必须回答 | **绝不能**自动推出 |
|---|---|---|
| 约定接受 | 哪个约定版本，由谁依据什么委托接受 | 已实现、已验证 |
| 证据评价 | 哪个 claim、对象版本与覆盖，有何证据 | 动作许可、风险接受 |
| 动作授权 | 哪个主体，可对哪些对象产生哪些效果 | 方案正确、结果成立 |
| 委托关闭 | 哪个委托，依据哪条规则及哪些事实关闭 | 已部署、用户价值已实现 |

- 探索任务可以先取得探索授权再形成尚未接受的候选；已知缺陷可以被有权者作为**明确例外**接受，但原来的 FAIL **不应被篡改**成 PASS。
- **同名陷阱**：A2A 的 `state: accepted` 只是**投递接收**，不是 TPW 的 contract acceptance。工具输出与状态展示必须把两者放在不同语义域，不允许一个 `accepted` 字段跨层使用。

### 4.2 三态判定不能与阻塞状态、执行未知混在一起

新的评价记录采用 **PASS / FAIL / UNVERIFIED**，并绑定具体 claim：
`FAIL` = 有效观察反驳了预期；`UNVERIFIED` = 证据不足、观察无效或环境阻止结论；`PASS` = 证据在声明的对象、条件与覆盖内支持预期。

`BLOCKED` 继续作为**工作推进状态**；外部动作的 `unknown` 作为**效果待对账**的执行状态。它们不是 F verdict 的替代标签。**尚未进行评价，也不能伪装成"F 已经给出了 UNVERIFIED"。**

（这也是不直接重新接通旧 graph verdict 的原因之一：残留类型是 PASS/FAIL/BLOCKED，旧关闭判断按历史事件里的 verdict 字符串或 evidence kind 查找条件，**不能证明"当前候选的这个必要 claim 已被适用评价覆盖"**。这是复用旧代码的风险，不是当前生产入口正在发生的错误。）

### 4.3 独立性绑定对象与贡献

评价记录至少说明：`subjectRef / subjectVersion`、`evaluatorInstanceId`、`authorOrContributorRefs`、`evaluationKind(design-challenge | implementation-evaluation)`、`coverage / observationTime`。

运行时能检查明确不成立的情况：**同一实例换个 role label 不能登记为独立评价者**；已知实质代做该部分实现的实例不能对该部分自称独立。但**不同 session ID 也不自动证明独立性**。同时，正常质疑、反例与补证要求**不能一律算成作者贡献**——否则会被迫不断换 reviewer。职责组合可以灵活，**贡献记录不能被恢复、换名、换模型或替换实例清空**。

### 4.4 召回必须改变"哪些依赖仍然可用"

只加 `returnsTo` 还没有实现召回。期望的运行行为（例：E 发现现有 revision 含义与计划假设不一致）：

1. E 提交受影响结论、事实与影响，**不自行改业务含义**；
2. 运行记录把**消费该结论**的相关任务标成"需要重新确认依据"，**不暂停无关工作**；
3. Driver 路由到该语义的**实际决定责任**——可能是 C，而不是因为问题发生在代码里就一律找 D；
4. 新决定引用旧决定并说明替代或仍适用的范围；
5. 依赖任务**显式采用更新后的绑定**再继续；旧报告保留，但不能自动满足新版条件。

机制需要 `consumes[]` 与**版本化结论**，不需要一个自动理解任意文字的依赖图谱。**已声明依赖的失效传播由运行时做；专业影响范围不明确时由责任方判断**——这正是"程序足够性由 Driver 检查，实质足够性由专业责任评价"。晚到结果**不能全部丢弃**：可能仍覆盖未变化的部分，应保留其对象与时点，由当前消费方判断可复用范围，而不是"晚到即无效"或"到达即通过"。

### 4.5 归档 ≠ 关闭；未完成工作按 dispatch 统计

`dismissGovernedTeam` 目前按 `reportCount === 0`、`reserved/provisioning` 判 pendingTasks。**角色累计报告数不能代表当前任务完成。** 增加 dispatch 记录后，归档/恢复都应按**本次委托状态**重建未完成工作。

同时：`orchestra_dismiss` 继续负责停止与归档，**不因专业验收未完成就不能停团队**。归档记录"已关闭 / 未关闭 / 放弃 / 待恢复"的真实情况；**archive 不是 completed 的另一种拼写**。

### 4.6 诚实限定"运行时真的成立"的范围

这些改动可以让 Orchestra 在**自己控制的入口**上保护身份、版本、接受来源、独立性条件、召回与关闭资格。它们**不会**自动限制一个仍持有广泛 Bash 权限的 agent 在工具外产生的所有效果。**方法绑定不是沙箱，`authorityRef` 也不是沙箱。**

涉及发布、迁移、外部写入等实际效果时，必须用宿主现有权限或相应动作入口实施限制；仅记录授权字段只能证明记录存在。产品声明必须区分两种保证：**"编排契约不允许继续"** 与 **"宿主已强制阻止该效果"**。

## 5. 批次（按评审重排）

> **不先做 42 篇清洗。** 先贯通一条纵向链，否则会出现"清洗完了，却没有任何对象承载本次绑定"。

### 第一批 · 可恢复的实例委托，贯通一条真实交接链

- 稳定**意图 ID**、真实委托引用、固定输入、责任绑定、方法版本、报告关联（`§3`）。
- 用**少量代表方法**先贯通：局部缺陷修复、跨模块设计、行为 claim 评价。
- 报告写入、记账、通知、turn-stop 的缺口**在这条链上一起解决**（`§7`）。
- **验收不是"字段都有"**，而是：同一任务在失败、重试、角色复用与恢复后，仍能回答**同一份委托是什么、已交付什么、缺什么、该由谁继续**。

### 第二批 · 评价、接受、召回、关闭接到当前工具契约

- 先支持两个有区分力的任务：**已有契约的局部修复**（复用已有 A–D，只调必要 E/F，不强制加 architect 或设计 gate）；**新增共享承诺的变化**（明确 B/C/D 的决定对象、设计挑战与实现后评价；上游语义问题只召回相关依赖）。
- 在 `orchestra_report` 等**当前入口**上承载结构化事实与有效处置，复用现有存储接缝。
- **不恢复那 16 个微状态机工具**，也不把 Driver 变成逐节点填表的人。

### 第三批 · 全量方法包与角色选择面（v1 的"P1"）

- 42 篇全量注册保留；需要控制的是**上下文暴露**与**错误的默认适用性**。
- 来源副本/消费视图分离、包内引用解析、选定 Profile 的责任心智模型、方法分节绑定、执行中按需补充、`verifier` 能力修复、`orchestra_topologies` 角色库输出。
- `orchestra_topologies` 必须**同时改输出 schema、实际返回与 render 文本**——只在 JSON 里加字段、模型常读的渲染文本却不呈现边界，等于没解决。
- **本批验收只能称为"方法分发与角色选择信息可用"**，不得宣称 TPW 的专业语义已经在运行时成立。

## 6. 验收：评审给的最小反例表（实现方须逐条证明）

> 以下是**要求实现方证明的行为**，不是已经运行过的结果。

| # | 反例 | 必须观察到的结果 |
|---|---|---|
| 1 | 工具可写，但本次没有对应动作授权 | 不因 preset、skill 或 dispatch 自述获得授权；编排入口明确拒绝或返回实际 authority |
| 2 | 同 `dispatchId` 重试；同 ID 改内容；新 ID 用相同任务文字 | 分别为**复用既有意图**、**明确冲突**、**合法新任务** |
| 3 | 报告已提交，通知失败后重启 | 报告不重写、不重复记账；待通知事实可恢复，**不能靠 worker 重做来推进** |
| 4 | 发给协作者一条成功的进度消息后结束 turn | **不能**被误认成向指定接收方完成本次交付 |
| 5 | 测量环境坏了；有效观察发现实现违反约定 | 分别为 `UNVERIFIED`、`FAIL`，不能互相替代 |
| 6 | 实现者换一个角色名提交"独立 PASS" | 不满足独立性条件；正常 reviewer 反馈又**不应**自动导致其失格 |
| 7 | 上游某项语义改版，另一个车道不依赖它 | 只阻止受影响依赖继续；旧 PASS 不覆盖新对象，无关有效结果保留 |
| 8 | 角色旧任务已有报告，新任务未完成时归档/恢复 | 新任务仍被准确列为未完成；**归档不冒充专业关闭** |
| 9 | 任务绑定方法 v1，插件升级到 v2，或引用目标不可达 | 不静默换版、不伪造已加载；明确恢复原绑定或报告缺失 |

## 7. P2 三缺口的修订修法

### 7.1 派发身份（原 v1 的 2.3）

- `dispatchId` **由发起方为一次意图生成并持有**；同意图重试**复用**，新意图另建。
- 另存 `payloadDigest`：**同 ID 同内容 → 返回既有结果；同 ID 不同内容 → 明确冲突。**
- 目标对象版本、绑定版本、方法版本不得在同一 ID 下静默变化。
- 缺省时由工具铸造并**在返回值中给出**，工具说明要求重试时复用该 id。
- 投递仍传 `idempotencyKey`，但保证收窄为 `§7.2` 的表述。

### 7.2 投递保证的准确表述

当前 A2A 路径**先 followup/inject 或追加 inbox，再记录 receipt**，存在"已入队、回执未持久化"的窗口；单文件 CAS 也不是跨报告文件、`team.json`、消息投递的事务。因此：

> 保证 = **同一逻辑意图只产生一份有效任务记录**；投递允许重试，但**重复投递不得产生第二次逻辑执行**；无法判定效果时保留 `unknown`，先对账，不盲目新派。
> **"消息恰好一次"与"任务效果恰好一次"分别取证。**

Session、native subagent、首次懒加载、恢复后继续**四条路径都要覆盖**，不能只给现有 Session 投递加一个参数。

### 7.3 交接成功的判据（原 v1 的 2.1）

`tool/result.isError === false` 是**必要改进，不是完整定义**。至少要建立：**本次 dispatch → 本次产物/明确阻断 → 对应接收方 → 已持久化或已接受投递的事实**。普通协调消息不能替代交付；结构化业务失败也不一定表现为 `isError=true`。

同时修正：`notifyDriverMilestone` 吞掉通知错误 ⇒ report 工具返回成功**不证明** Driver 已被唤醒。**不能让 worker 因通知失败重复生产已经提交的报告**；应由通知恢复路径补交接。

### 7.4 待通知事实与恢复入口（原 v1 的 2.4）

- 需要**明确触发条件**的待投递记录：运行期**有界重试** + **启动时重新接续** + **接收方恢复时对账**。复用现有插件生命周期与定时能力，**不需要新服务**。
- `noticeFailures` 保持"诊断 breadcrumb"身份：它有数量上限、保存的是失败说明。**未完成的待办不能因为超过 20 条就消失**——诊断记录与待交接事实**分开**。

### 7.5 旧 gate 双写（原 v1 的 2.5）

**先证明它仍在你打算支持的真实入口上**，再决定是否修；否则可能为吸收 TPW 而重新维护已退出主路径的旧机制。

## 8. 方法与语料的处理（修订版）

### 8.1 两件产物：来源副本 + 消费视图

| | 来源副本 | 消费视图 |
|---|---|---|
| 内容 | 固定 commit 的**逐字节副本**，**不手工改写** | 从来源副本**机械生成**，用于 skill 加载 |
| 来源锚点 / Status / 验收段 | **保留** | 可不送入日常上下文 |
| 维护 | 唯一来源 | **不独立维护**（一份来源 + 一个派生表示，不是两份权威） |

### 8.2 清洗规则（对消费视图生效）

| # | 规则 | 实测影响 |
|---|---|---|
| R1 | 去掉标题的候选/历史状态后缀（原始状态留在来源副本） | 42/42 |
| R2 | 隐藏 Status 行——**但先区分"历史验收状态"与"适用范围/资格限制"**，后者保留 | 34/42 |
| R3 | `## Source anchors` 到文件末尾不送入日常上下文（**不从来源副本剥掉**） | 507 行 |
| R4 | 独立引用行可从消费视图隐藏，仍能回到原始出处 | 1 行 |

**实测（只读跑测）**：`606,146 B → 493,112 B（−18.6%）`。剩余 ≈8% 是**句中**引用，需要重写句子才能删——**不动**。

### 8.3 包内引用必须可解析

v1 的"句中文字不动"标准不够：**文件文字不变、引用目标却失踪，消费语义一样会坏**。方法正文会引用 `charters/README.md`、其他 guide 或方法；只输出扁平的 `methods/<slug>.md` 时，必须说明这些引用**怎样解析**，而不是假设模型知道新目录布局。

### 8.4 统一 header（重写）

> 本文提供判断方法，**不因被选择或加载而产生接受、权限或门禁**。
> 本次适用性与动作边界来自**所引用的有效委托、政策与已接受承诺**；dispatch **记录**这些绑定，**不自行创造**它们。
> **工具能力与动作授权必须分别满足。**
> 发现冲突或缺失的关键判断时，说明受影响对象、事实及影响，返回**拥有该决定权**的责任方；**只暂停依赖该问题的工作**。

### 8.5 绑定 ≠ 封闭

- **初始绑定**：Driver 根据当前任务指定**首先需要**的方法与原因。
- **执行中补充**：实例在**已有委托内**补充所需方法并记录用途；涉及新增判断责任或改变承诺时，再召回相应责任方。**追加阅读不等于追加权限**，也不必每次找 Owner。
- **"一篇文件"不是最细的适用单位**：`interface-contract-and-retry` 明确把接口契约与重试语义分成可独立选择的部分；只研究只读接口，不应因为加载整篇而被要求设计幂等记录。方法绑定可带 `sections` / `purpose`，但**不需要据此建立新的知识图谱**。

### 8.6 skill 注册与索引

- 名字 `pw-<slug>`，`description` 取选择表的**任务触发语**；**不做单值 judgment 机械提取**（第三列不统一，且存在跨多个判断函数的方法）。
- 注册集合 = **42 篇方法 + 2 个辅助 skill（`pw-method-index`、`pw-responsibility-backbone`）**，二者**分开计数**；"每个注册名都能在 INDEX 里找到"的双向一致只约束方法集合，不把自己的辅助注册排除在契约外。
- 摄取器硬性失败条件：无写死 commit、表与文件非 1:1、`Source anchors` 不是末节、`--verify` digest 不符、**包内引用目标缺失**。

## 9. 角色选择面与 persona

- `RolePresetSpec` 增 `judgmentCapabilities[]`（选择提示）、`concerns[]`、`chooseWhen`、`decideNot`；**方法默认值仅作建议**。
- `orchestra_topologies` 增角色库输出；**同时改 schema、返回与 render 文本**；测试断言覆盖 catalog 全部预设 id。
