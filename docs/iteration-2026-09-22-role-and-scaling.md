# 2026-09-22 本轮范围追加：Driver 伸缩与角色质量

> 来源：Owner 在 0.1.7 升级执行期间追加的明确要求。**本轮实现，不是远期待办。**
> 适用于当前 A2A + 编排升级；host 确定性交付层本轮仍只优化 plan，不实现。
> 与更早的“仅兼容迁移”任务说明冲突时，以本文件为准；不覆盖安全/发布边界。

## 1. 产品目标

Driver 与用户明确 mission 后，能选择最小够用的协作方式，并在任务推进中调整成员和车道。独立 Session 的价值是独立 preset/能力与协作身份，不是独占持久化或可见性；原生 continuable subagent 本来就有日志和续跑。

能力不是按人数强制递增的套餐：一次高风险发布即使只有一个执行者也可能需要交付门；很多只读调研者也不因此必须进入交付层。

- 可直接完成的任务：driver 自己做，无强制建队、任务卡、报告文件或审查角色。
- 适合有限委派的工作：一个或少量原生 subagent，按需续跑，无强制团队章程。
- 需要独立 preset/cwd/权限或持续跨会话协作：少量 Session 角色，A2A 独立可用；需要共享名册/动态车道时才建 Orchestra team。
- 更复杂的团队：Session 与 subagent 可混编，成员按职责增减，不按模板强制配齐。
- 确定性交付层：后续显式启用，不能给上述轻量路径增加隐性治理负担。

## 2. 派发逻辑的归属

**Driver 判断意图与组织方式；host 校验能力与执行事实。**

- `src/orchestration-principles.ts`：薄的常驻 driver 指引 + 按需加载 playbook；先选择执行方式，不从“必须画图”开始。
- 既有角色/拓扑解析、blueprint、dispatch、原生 subagent seam：验证 backend 实际能否满足请求，选择完整创建/恢复/投递路径；不能满足就类型化拒绝，不静默降级。
- 任务具体目标、范围、输入、完成条件、交接对象属于 dispatch；不固化进 persona。
- 不新增复杂度评分器、另一个 LLM 分类器、通用策略引擎或微状态机工具面。
- 现有 topology 未声明 execution 时继续保持 Session 语义；driver 可以为新任务显式选 subagent，不借此静默改变旧拓扑。
- 不以“角色需要问用户”为 Session 常规理由：团队成员问题回 driver，成员审批仍 never；权限由宿主强制，不靠 persona。

## 3. 运行中新 mission → 当前 team 的 lane

保留一个 team 与一个最终收束者；新 mission 的目标、范围/约束、完成条件与既有工作的关系要可追溯，不只是新加角色名字。

- Driver 与用户对齐新增目标，说明复用谁、新增谁、是否影响既有工作，再按既有批准边界应用。
- 优先复用现有合适角色；**新增车道不等于必须新增成员**。
- 新角色仍 reserve-only，首次派活才物化；不因用户讨论了一个想法就开会话。
- 原 mission/批准事实不能被新目标覆盖；新增 lane 保留自己的目标和参与角色，模型看板能看到增量。
- 接管/归档/恢复后仍知道各 lane 为什么存在、由谁处理；不能只恢复 roleId 列表。
- 在现有 team/lane seam 上做最小数据与工具扩展；不借机实现第二部分节点账本、租约、Git 交付门。
- 若新 mission 不属于同一项目/权限边界，明确说明不能硬塞本队，走独立工作区或后续显式决策，不悄悄扩大 cwd/sandbox。

## 4. 角色 persona：高质量的薄

Persona 不是完整 workflow 手册，也不是“多年专家”身份叙事。常驻内容只保留会改变角色行为的差异：

1. 对什么结果负责；
2. 优先如何取得足够证据/做判断；
3. 哪些决定不属于自己；
4. 什么情况下继续、报告阻断或升级给谁；
5. 最小完成与交接条件。

公共纪律只保留一份最小公共段；角色特有的方法不能被通用禁令淹没。宿主工具契约已有的 schema、路径说明和全部故障教程不重复塞入每个 persona。通常保持 `complete:false`，保留 DSH 的工具和环境上下文。

- implementer：实现范围内最小正确改动，核对真实执行路径，前提推翻时报告，不靠补丁掩盖；报告验证和未验证，不给自己放行。
- investigator：将观察与假设分开，比较竞争解释，用最低成本反例定位；交付可行动修复范围，不默认接管实现。
- reviewer：审指定候选与范围，发现需位置/触发/影响/证据；区别缺陷、未知和偏好。复审聚焦修复与其影响面，但**不能因轮次上限隐藏新发现的阻断缺陷**；到限升级而非无限审。
- verifier：核验执行证据的来源、条件、结果与覆盖，不重复扮演 reviewer；会写缓存/构建产物的验证不得冒充 read-only 可执行。后续交付层由 host 执行，verifier 负责解释，不成为第二个读数真源。
- planner：交付让执行者无需猜关键前提的任务说明；不强求所有任务都有 planner，不把更多计划当进展。
- architect：解决实际结构边界/迁移取舍，明确约束、替代与代价，不做全局无边界重设计。
- researcher：来源支持的事实、推断与未知分列；把研究交给决策者，不自行取得决定权。
- oracle：解决被升级的具体不确定性，给建议、依据、置信边界与误判后果；不是每步的审批人。
- hardening-auditor：可达风险、复现/无法复现原因、优先级与修后复验；不以纯假设扩大范围。

不必新增更多稳定角色。角色组合应能说明“谁执行、谁检查、谁处理争议、谁收束”，但不要求每次四者都是不同会话。需要独立审查时才确保非作者/fresh context。角色可长期稳定，重要评审上下文可刷新，不等于重用无限长的会话。

## 5. 新 preset 的按需 playbook（本轮交付）

当现有 preset 无法满足真实任务时，driver 有可加载的指南，而不是临时猜 DSH 内部结构。

指南至少覆盖：

- 判断仅改 dispatch / 加现有 skill / 选已有 preset，还是确需新 preset。
- 说明新增工具、权限、成本和适用任务；在已有授权内复用，新增能力/安装/权限扩大须用户批准。
- 用 **0.1.7 真实原生注册/组合机制**创建；不继续写旧目录 roots，不自行实现另一套 preset 管理器。
- Persona、能力组合、权限/模型与任务输入分开，避免全工具模板；模型未声明继承 driver 的已决口径。
- 验证实际工具、persona、审批/沙箱和新会话/恢复表现；无法验证就保留缺口。
- 说明变更对已有 Session 的限制，不承诺热切 preset；必要时新建实例、携带自包含交接。
- 提供一个最小、目标版本可运行的定制示例，并确保包内资产与指南实际随 npm pack 发布。

## 6. 本轮验收（必须走真实生产 seam）

1. 最小任务不因指引被迫建 team；A2A standalone 与原生 child 路径仍独立可用。
2. 明确需要独立 preset/read-only/cwd 时不会被错误选成 subagent；不符合原生能力的请求被拒。
3. 真实建队 → 读回 → 首派，persona/tools/权限与冻结选择一致；含 subagent persona/toolFilter 保真。
4. 运行中新增 mission，可只复用已有成员形成 lane；原 mission 未覆盖；需要新增者仍懒创建；看板显式显示目标和角色。
5. 恢复后能查到增量 lane 与角色身份；既有生命周期回归继续通过。
6. 各 persona 在可运行组合中确实生效；无已删除工具、虚构运行时 cap、要求成员询问用户等矛盾指令。
7. playbook 可被发现/加载，最小 preset 示例通过目标版本注册与新会话校验；静态检查不能代替运行期结论。
8. host 交付层 plan 明确是独立可选层，并从本轮实际输出的角色/lane/backend 接口衔接，不另造第二个 team。

## 7. 执行与环境

源码与 prompt/preset 是同一个协作产品面，实施者需一起验证，不只改散文。审计先确认新 API，单一 writer 串行改动；最终 fresh reviewer 检查派发灵活性、角色差异、组合闭环与权限边界。
