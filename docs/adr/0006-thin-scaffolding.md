# ADR-0006 · 脚手架方向：轻度替换

- 状态：Accepted（批准方式已由用户 2026-09-15 拍板，见文末）
- 日期：2026-09-15
- 来源：用户口述（2026-09-15）+ 本轮代码核实

## 背景

用户口述：

> 我们这个插件分两个部分，一部分是 A2A，一部分是 multi-agent workflow。
> 我们自己打磨的主要是**编排原则** —— 一个 mission 应该怎样被拆分、怎样设计 DAG、
> DAG 里边哪个地方是循环。难点就在**怎么在尽量轻的脚手架的情况下，有一些脚手架
> 来帮助整个 DAG 能跑完**。但现在跟当时做这个项目时不太一样了，因为现在
> 比如 deepseek-v4.1-flash 的指令遵循能力非常强，**就更不需要特别厚的脚手架**。

现有实现把"编排 = 协作宪章"做成了重机器：草案 append-only revision →
`/team approve <draftId>@<revision>`（唯一硬批准）→ `orchestra_freeze`（digest）→
`orchestra_create(frozenRef)`，运行时再叠 17 类 graph 事件 + 每次决策 CAS。

本轮核实到三条支持"厚得不必要"的直接证据：

1. `orchestra_spawn` **是死工具**：注册了、有完整参数表，但 `rejectDirectGovernedSpawn()`
   无条件抛错（`src/orchestra.ts:1341`，调用点 `:2830`）。
2. 受治理 roster **创建即锁死**：唯一能改的 `orchestra_apply_amendment` 在 roster 有差异时
   只返回 `status:"pending_runtime_actions"`，不创建任何会话（`src/orchestra.ts:3291`）。
3. **受治理主路径从未端到端跑通过**，且结构性无法自我验收（需要用户命令）。

## 决定

**方向 = 轻度替换**：宪章与 graph 记账压成薄核心。

### 保留（模型不会自己发明、且结构性必需）

- **编排原则**（P1–P15）作为 driver 的可教文本 —— 这是产品本体，一个字不缩。
- **机器可校验子集**（可达性 P9 / 完成权归属 P6 / 有界性 / 无环性）留在 validator：
  能证明的不要靠纪律。
- **有界 Loop 的运行时强制**：attempt 上限 + 三个出口 + deadline。
- **批准门**（是否保留见下方 Proposed）。

### 压掉（记账仪式，不改变结果）

- charter 的 append-only revision + digest + freeze 三步 CAS → 一份文件 + 一个批准标记。
- graph 的 17 类事件日志 → 运行态只留**一份** `run.json`（loop / attempt / 终态），
  投影从它算，不再重放事件。
- `orchestra_reconcile` / `orchestra_graph_reconcile` 这类"人工 checkpoint"工具 ——
  状态即文件时，人工对账没有存在理由。
- 每次决策一次 CAS → 单写者（driver）+ 文件版本 CAS。

### 迁移

与 **ADR-0002** 同批做：宪章的家就是这里要改的东西，分两批做会做两遍。

### 纪律

- **不得静默降级**：旧的 `/team approve <draftId>@<revision>` 形式必须继续可用；
  无 protocol 的 legacy 拓扑继续可读（既有契约）。
- 被删或改语义的工具，README / STATE / 工具描述必须同步 —— 不允许出现
  "文档说能用、实际已经没了"（`orchestra_spawn` 就是这一类，它已经在骗人了）。

## 后果

- **测试会净减少，这是必须付的代价**：现有 193 个测试里有相当一部分在测这套仪式。
  删仪式必须**同时新增**覆盖"薄核心仍能跑完"的测试，而不是简单删掉断言。
- **风险**：薄核心一旦缺硬约束，弱模型画不出可跑的图。
  缓解 = validator 保持 fail loud + 原则文本不缩水 + attempt deadline 仍在运行时强制。
- 与 ADR-0002 的交互：文件即文档之后，"driver 会话独占文档"这个前提消失，
  薄核心才有可能（读取实现已经解耦）。

## 批准方式：用户已拍板（2026-09-15）

**用户原话：**

> 连这个 `/team` 都不需要，你可以用更简单的方式，直接让用户回复一句"启动"就行了。
> 打 slash 其实很麻烦。

因此**批准不再要求任何斜杠命令**：用户在对话里回一句"启动"（或同义的一句肯定）即可。

这**推翻了**这个插件原来的核心设定——"自然语言不算批准，必须敲
`/team approve <draftId>@<revision>`"。推翻是有意的，用户明确要求它。

### 但下面两条必须活下来

这两条不是形式，是那个设定真正在保护的东西。换成一句白话之后，它们要靠**检查消息来源**
和**记住给你看过哪一版**来实现，而不是靠命令语法：

1. **只有你本人能批准。**
   批准必须来自一条真正的用户发言。插件自己插的提示、以及别的会话（包括插件建的角色会话）
   发过来的消息，都不算。**否则**角色会话可以替你"批准"，那道保险就形同虚设。
2. **批准绑定的必须是你看到的那一版。**
   系统记住"最近一次给你看过的计划是第几版、内容编号是多少"。如果我在给你看过之后又改了计划，
   你这句"启动"会被拒绝生效，并重新把计划给你看一遍。

### 我知道的风险（写在这里，不藏着）

一句话的肯定天然有歧义。如果恰好有一份计划在等你拍板，而你说"启动"其实是在说别的事，
系统会当成同意。

缓解办法：只在**确实有待批准的计划、且内容没变**时，才把一句明确的肯定当成同意；
含糊的回复一律当作没批准，再问你一次。

### 兼容

`/team approve <draftId>@<revision>` 这个老形式继续可用，不删——只是不再是必须的。

### 一句话界线

我按"**批准这一步不再需要斜杠命令**"来实施。`/team <目标>` 作为发起任务的入口是否也去掉，
用户没有说，**不在本次改动范围内**；要动它请另行指示。

### 实现（2026-09-15 已完成）

- **怎么知道你说了一句"启动"**：插件订阅 `session/event`（宿主提供的"每次日志追加之后"的广播），
  只挑出**你本人发的**文本消息。别的来源一律不看。
- **谁来认这句话**：`approvePendingDraftFromUserMessage`
  （`src/orchestra.ts`）。命令那条路(`/team approve …`)和新路**共用同一个记录函数**
  （`recordCharterApproval`），所以两条路写出来的记录**逐字节相同** ——
  区别只在于你是怎么说"是"的，不在于记下了什么。
- **待批准的草案怎么找**：从记录本身推导（"这个会话写的、还没有批准覆盖的最新一版"），
  不另存一个"待批准指针"—— 指针会和记录漂移，一漂移，批准就可能绑到你没看过的东西上。
- **记录里写清出处**：新路的 `commandId` 是 `message:<会话 id>@<消息序号>`，
  也就是"**就是这条消息批的**"，事后可以回查你当时到底说了什么。
  同时 `CharterApproval.source` 从写死的 `"user-command"` 改为
  `"user-command" | "user-reply"` —— 这个字段本来就在回答"用户到底做了什么"，
  让它对一句白话回复撒谎，比缺这个字段更坏。

### 实机验证（2026-09-15，已完成，端到端）

在真实实例里跑通了完整的一条链，这是这个项目里**受治理流程第一次跑到这么远**：

| 步 | 实际发生的事 | 证据 |
|---|---|---|
| 1 | 模型自己调 `orchestra_draft` 产出计划 | `orchestra/charter/records.json` 出现 `charter-draft` 记录 |
| 2 | 用户（我代敲）回了一句 **「启动」** | — |
| 3 | 监听器记下批准 | 出现 `charter-approved`：`commandId = message:session-38632dba-…@62`、`source = "user-reply"` |
| 4 | driver 被叫醒，自己继续走 | 出现 `charter-frozen`，其 `approval` 指向第 3 步那条批准，digest 完全一致 |
| 5 | 会话日志仍然可读 | `check-session-readable.mjs`：ACCEPTED（117 个事件） |

另外两条也验了：**再回一次"启动"不会产生第二条批准**（幂等）；**回一句"我再想想"什么也不做**。

**实现时被自己的测试抓到两个错**（都已修）：

1. **"只有用户能批准"这条原本只写在监听器里**，没写在真正落记录的函数里。
   测试直接调用那个函数，于是"插件来源的消息"也能批 —— 保证写在调用方，一换调用方就没了。
   现已在落记录的函数里也检查来源。
2. **记录写死 `source: "user-command"`**，一句白话回复会被记成"用户命令"。已修（见上）。
