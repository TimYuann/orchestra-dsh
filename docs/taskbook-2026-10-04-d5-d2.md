## 项一 · D5（**首批内** —— 首批自身交付不达标）

### 事实

`orchestra_team` 在 D1 修复后能正常返回了，但它**对模型暴露的只有一行 prose 汇总**，例如：

```
… dispatches: 3 total, 0 undelivered | handoff notices: 3, 0 awaiting the driver
```

而它自己声明的 schema 里**有逐行字段**：`dispatches[].dispatch_id / open / report_id / superseded_by`、`handoff_notices[].notice_id / state / driver_state / attempts / path`——**这些从未进入渲染文本**。

### 为什么这是首批的问题

方案 §3.2 首批保留列里写着"**按派发显示未交付工作**"。账本在结构化层成立了，但**读这份看板的人（driver）看不到"哪一条派发还开着、哪一条通知卡在谁那里"**。

实测佐证：demo driver 在被要求回报逐条状态时，明确拒绝用读盘去补工具没返回的字段——"渲染文本里没有，我不能替你补"。它是对的，缺口在渲染层。

### 不是这个

**不是**"dispatch 摘要行缺 `profile_ref` / 方法绑定身份"。`profileRef` 与 `methodBindings` 在 `TeamState.dispatches[]` 里**已经落盘、且我已核对到**（见 `docs/live-run-2026-10-04-first-batch.md`）。缺口在**渲染层**，不在投影字段是否存在。

### 要求

1. 让**逐行状态对模型可见**。driver 至少需要：哪条 dispatch 仍开着（未交付 / 未回收报告）、哪条已有报告、哪条 notice 处于待处理 / 已被认领 / 卡住。
2. **渲染必须仍然有界**——不要整块 dump 账本。条数增长时要有明确截断策略（例如只列未闭合项 + 一行计数，并说明截断了多少）。
3. 保持"渲染文本与结构化行来自**同一份投影**"这条既有纪律（`dispatchBoardTextFromRows` 的设计意图），不要另算一份。
4. **验收**：加测试断言——账本非空时渲染文本**包含逐条标识与状态**（至少覆盖 open 与非 open 各一条、notice 的 `state` 与 `driver_state`）；并断言**条数很大时渲染仍然有界**。
5. 如实写明本次证明的边界。

## 项二 · D2（**范围外**，Owner 已单独授权；单列 commit 并标明"首批外修复"）

### 已核实的缺陷

- `src/session-blueprint.ts:624`：`const missing = capabilities.composition.filter((name) => !declared.includes(name));` —— **普通 `includes`**；
- `capabilities.composition` 由 `capabilityTools()` 把 **`requiredTools`（工具名，如 `read`/`edit`/`write`/`bash`/`grep`/`glob`）** 并入，而 `declared` 却是**目录行 id**（`tool-fs` / `tool-bash` / `tool-fs-search`）；
- 同文件 `:575` 就有**别名感知**的 `hasCompositionTool` + `COMPOSITION_ROW_TOOLS`（`:1112 / :1153 / :1155` 在用）⇒ **同一份"构图工具证明"存在两套匹配语义**；
- 后果：**角色只要声明了 `requiredTools`（工具名）就必然全缺、永远过不了**。实测代价 = demo driver 6 个 revision / 约 1.1–3M token；
- 报错文案还把方向指反：`catalog composition does not declare required compositionTools: read, edit, write, bash, grep, glob`——读的人会去补错的那一侧。

### 语义裁定（Oracle 已定）

采用 executor 提出的 **(b) + (a) 组合**：

- **(b) 两个证明面分开**：`requiredTools`（工具名一侧）应针对**可见工具名 / `hostToolNames`** 证明；`compositionTools`（行 id 一侧）针对**行 id** 证明。**不要把两个命名空间并进同一个集合再比。**
- **(a) 同面比较时用别名感知匹配**：同一命名空间内比较时走 `hasCompositionTool`，而不是普通 `includes`。

### 要求

1. 按上述裁定改语义。
2. **保留守卫的本意**：能力确实无法证明时**仍必须拒**，不得因为放宽而变成恒真。
3. **修报错文案**：说清"要求的是哪一侧、声明的是哪一侧、两者命名空间不同"，让下一个实施者不用猜。
4. **验收（先红后绿全都要）**：
   - (a) 角色声明**工具名** `requiredTools` + 目录预设 → **现在应通过**（这条在基线上是先红的）；
   - (b) 能力**确实缺失**时**仍然拒绝**（负例，证明没被放宽成恒真）；
   - (c) 相邻两个守卫不回归：`compositionTools` 里出现 `orchestra_*` 仍拒（`orchestra-topology.ts:1234`）、`orchestraTools` 里出现 host 工具仍拒（`:1237`）。
5. **边界**：不得改动首批引入的语义；本项单列 commit，报告标题标明"首批外修复"。
